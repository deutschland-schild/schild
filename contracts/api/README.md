# Dashboard APIs

- [client-dashboard.openapi.yaml](client-dashboard.openapi.yaml): `schild` dashboard API, full visitor IPs locally. Includes the server check: hosts, host reports and agent enrolment ([../host-check.md](../host-check.md)).
- [lab-dashboard.openapi.yaml](lab-dashboard.openapi.yaml): `schild-lab` dashboard API, never any visitor IP.
- [gateway-agent.openapi.yaml](gateway-agent.openapi.yaml): agent API of `schild`, read only except the writes of `agentapi.WriteOperations`, each with its own scope: rule repositories and rules (`rules:write`), single blocks (`blocks:write`), rule exceptions (`exceptions:write`), the crawler policy (`crawlers:write`); on its own loopback listener, bearer tokens from the host CLI; the gateway serves it bundled into one JSON file at `GET /agent/v0/openapi.json` (`contract/agentapi/openapi.json`, written by `make contracts-sync`); never a full visitor IP (keyed pseudonym and /24 or /48), visitor text marked `x-untrusted`. Reuses schemas of the client document by reference, among them the rule repository and rule schemas (same paths and schemas in both APIs).

OpenAPI 3.1, schemas are JSON Schema 2020-12. Schemas of signed payloads are referenced from the contract schemas (`../signal.schema.json`, `../feedback.schema.json`, `../events.schema.json`) instead of being copied; the lab document reuses shared components of the client document by reference.

Fixtures in `fixtures/<client|lab|agent>/<operationId>[.variant].json` are realistic example responses for UI development and tests; the app-kit mock serves `<app>/<operationId>.json` for its operation. Each one validates against the success response (200/201/202) of that operation, variants starting with `problem` against `Problem` (`cd contract && go test ./apispec`). They use only documentation addresses (RFC 5737 `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`; RFC 3849 `2001:db8::/32`), documentation ASNs (RFC 5398) where possible, and `.example`/`.test` names. No real people.

A fixture for an operation no component serves yet would go to `fixtures/pending/<client|agent>/` (there is none at the moment): `contract/apispec` validates it like the others, while the gateway's round-trip test, which wants a Go type for every fixture, reads only `fixtures/client/`.

Conventions every operation follows (checked by `TestConventions` in `contract/apispec`): a `default` response with RFC 9457 problem details (`code` is a stable machine-readable reason, `errors[]` points at invalid fields), `X-CSRF-Token` on every state change except first-run setup and login, `cursor`/`limit` on every list (`next_cursor` null at the end), `Last-Event-ID` on SSE streams, no `format` keywords (implementations differ), and no IP parameter or property in the lab and agent APIs (`TestAgentAPI` adds: GET only apart from the named writes, a description for agents on every operation, untrusted fields marked, no full IP in agent fixtures; `TestAgentBundle`: the served bundle is current and self-contained).
