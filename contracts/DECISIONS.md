# Decisions for contracts v0

Status: **v0, frozen 2026-10-26** after an adversarial review (D21, [CHANGELOG.md](CHANGELOG.md)); **v0.1** addendum the same day (D22); **v0.2** addendum by the initiator (D24). Decided by the contracts agent where the concept left details open; every item names its source. Items marked **OPEN** need a human decision; none of them changes the v0 wire format or check order. Concept references: docs/concept/13, 18, 20, 21, 23, 24.

## D01 Envelope: DSSE + Ed25519, one payload type per kind (E2)

- DSSE v1 with Ed25519, PAE as in the DSSE spec. Standard base64 **with padding, canonical only**; compact JSON, no extra envelope fields; at most 16 signatures. ([envelope.md](envelope.md))
- Domain separation twice: `payloadType = application/vnd.schild.<kind>.v0+json` per kind, and key **purposes** (`signal`, `feedback`, `ack`, `rules`, `checkpoint`). A key may only sign kinds of its purposes.
- Unknown or untrusted signatures are ignored, not fatal (TUF semantics); only the count of valid trusted signatures matters.
- Payloads are plain JSON objects with a `schema` field, **not** CloudEvents inside DSSE (deviation from concept 20 §3.2). Reason: the payload type already carries type and version; a k-of-n bundle has no single `source`; CloudEvents attributes (`type`, `id`) live on the SSE stream level instead. For lab-to-lab feeds (not in the prototype) CloudEvents inside DSSE stays the plan.
- E2 says "for signals only until v1": in v1 signals lose the site signature and get a token ([auth.md](auth.md)).

## D02 Signal `schild.signal/0.3` (E4)

- Exactly the positive list of MVP-01 plus three framing fields without data (`schema`, `id`, `kind: tip`). Compared with concept 18 §4.2 (0.2): no `ip`; no in-payload `auth` (moved to the auth layer so the payload is scheme-independent); no `match_shape`, `outcome`, `transport` (not on the E4 list).
- `id` is a random UUID v4, reused only for retries and copies to other labs (dedupe, ack).
- `time_bucket` is floored to a multiple of 5 minutes (5, 10 or 15 minute buckets all start there); schema enforces `:[0-5][05]:00Z`.
- Unknown fields are a `schema` error; a list of forbidden key names (IP, URL, headers, cookies, body, host, site, user agent, email, session, auth/token, ...) is checked first at any depth and returns `forbidden_field` for a clear signal in tests (T19).
- `action_sig` and `category` must not contain IP-like sequences (`n.n.n.n` with `.`, `_`, `/`, `-` separators); `action_sig` has no `?`, `=`, `:` or spaces.
- `origin.attribution` only `tcp_peer` or `trusted_proxy` (G5): requests with any other attribution never produce a signal.
- Review v0: free-text tokens follow `noLeak` (no IPv4, dashed IPv6, 7+ digit or 8+ hex runs), `action_sig` <= 64 characters, `agent.family` without dots, `asn` <= 2^24 - 1, `waf_rules` strictly ascending, forbidden keys normalised ASCII-only (lower case, without `-`, `_`, `.`), exactly one signature per signal or feedback envelope (signal.md).

## D03 request_sig canonical form

Line-based text `schild.request-shape/1`, method, path template, sorted unique parameter names, media type, sorted unique rule ids, then sha256 ([signal.md](signal.md)). A fixed test value is pinned in Go and Python. Path templating (ids to `{n}` etc.) is the client's job (MVP-02); it never includes host, values or IP.

## D04 Rule distribution: TUF-like, k-of-n by operator (E3)

- **Bundle = full state** of all network rules of a channel (`bundle_id`, default `schild-main`), not a delta: simpler atomic swap (B07), trivially gap-free resync. At most 500 rules, 1 MiB envelope; bundles over 32 KiB travel by reference (`ref` with sha256 of the envelope bytes).
- `version` strictly increasing (**rollback** rejected); same version with another payload digest is **equivocation** (rejected, signed proof). `expires` required, validity at most 31 days; `issued_at` at most 120 s in the future.
- Threshold: valid signatures by `rules` keys of at least **k distinct operators**, k = client `min_independent_operators` (floor 2 in schema **and** code, default 3). Several labs of one operator count once (concept 21 §2).
- TUF roles simplified for the prototype: the trust root is the client configuration (lab keys with purposes); the **checkpoint** plays the TUF timestamp role: signed by one lab online key, validity <= 10 min, re-signed every 60 s, names the newest bundle version + digest and withdrawal seq. No separate root/targets/snapshot files in v0.
- **Withdrawals** (emergency stop and single rules) are k-of-n like bundles, carry a strictly increasing `seq` and apply to bundle versions `<= up_to_version`; a later bundle is authoritative again. They can only remove network rules, never add.
- No transparency-log witnesses for now (E3 "vorerst ohne Zeugen"); `checkpoint.log` `{size, root}` is optional and reserved for them. **OPEN**: inclusion proofs with witness cosignatures before `challenge`/`block` (concept 20 §3.4).

## D05 Test profile and operator floor (E5)

- `schild.yaml` `profile: test` enables `test_profile.simulated_operators` (lab -> `sim-*` operator) so that labs of the one real operator count as independent in the local test lab and in the live test on own projects.
- The test profile is only valid with `mode: observe` (schema `if/then` and code) and `test_profile` is forbidden without it.
- Release builds (`-tags release`) refuse the test profile (`config.ErrTestProfileInRelease`), every test key and the `testkeys` package.
- **Prototype images for stage 2 and stage 3 are built without `release`**, because stage 3 needs the test profile and stage 3 must run the same image digests as stage 2. Alpha images are release builds. **OPEN** for the initiator to confirm.
- `min_independent_operators`: floor 2 enforced in schema and in Go (`config.Site.check`, `verify.Context.EffectiveThreshold`), default 3; a site can raise, never lower.

## D06 Language and dependencies (E6)

Go 1.24, `CGO_ENABLED=0` (**Go 1.25 since D24**, every module and the build images). Contract module dependencies: `github.com/santhosh-tekuri/jsonschema/v6` (Apache-2.0, JSON Schema 2020-12), `gopkg.in/yaml.v3` (MIT and Apache-2.0). The Python cross-check uses only the standard library plus `jsonschema` >= 4.18 (MIT); Ed25519 there is pure Python (RFC 8032 arithmetic) so the cryptography is independent of Go's as well.

## D06a Two implementations

The Go reference (`contract/`) and the Python cross-check (`contracts/tools/crosscheck.py`) are written from the same documents but share no code: different JSON parsers, different JSON Schema libraries (santhosh-tekuri/jsonschema vs python-jsonschema), different Ed25519 code (Go crypto vs pure-Python RFC 8032 arithmetic), different regex engines (RE2 vs Python re). Both were written by the same agent; the differential fuzzers reduce but do not remove that common-mode risk, so the red team (MVP-07) should write a third, independent checker for the SecLang subset. `make contracts-fuzz` runs a seeded SecLang fuzz (100,000 rules by default) and a pipeline fuzz (2,000 structurally mutated and re-signed vectors covering every error code) and fails on any disagreement.

## D07 Error codes and check order

Stable codes (`oversize`, `malformed`, `envelope`, `payload_type`, `signature`, `threshold`, `forbidden_field`, `schema`, `clock_skew`, `expired`, `validity`, `replay`, `channel`, `rollback`, `equivocation`, `duplicate_rule`, `seclang`, `evidence`, `config`, `test_key`) with a fixed order of checks ([vectors/README.md](vectors/README.md)). Both implementations must agree on the code, not only on valid/invalid, which makes the cross-check stricter. Acks reuse these codes as rejection reasons (plus `quota`, `revoked`).

## D08 Strict JSON

UTF-8 without BOM, no duplicate keys (both parsers would keep the last value: a classic smuggling vector), no escaped lone surrogates (Go and Python decode them differently), nesting depth at most 32, finite numbers only, no trailing data. `1.0` is an integer as in JSON Schema; Go normalises such numbers before typed decoding.

## D09 Portable regex in schemas

Schema patterns use only syntax on which ECMA-262, Go RE2 and Python `re` agree: no `\d \w \s`, no lookaround, no backreferences, repeat counts <= 1000. ECMA `$` means end of input; Python's `$` also matches before a final newline, so the cross-check translates `$` to `\Z` (documented in `crosscheck.py`). A Go test rejects non-portable patterns. No `format` keywords are relied on (implementations differ); timestamps use explicit patterns plus a parse check (impossible dates such as Feb 30 are `schema` errors).

## D10 SecLang subset (K7)

Allowlist only ([seclang-subset.md](seclang-subset.md)): one SecRule plus up to 3 chained lines; request-phase variables only; `REQUEST_HEADERS` needs a name and never Host/forwarding headers; no `REMOTE_ADDR`, `SERVER_NAME`, `GEO`, `TX`; no `@ipMatch*`, `@geoLookup`, file operators, `@unconditionalMatch`; negated and numeric operators only in chained lines; `@rx` restricted to a portable subset and **must not match the empty string**; ids `7700000..7799999`; `ctl`, `allow`, `skip*`, `exec`, `setvar` (except raising the anomaly score), `nolog` and every other action outside the list are rejected; `msg`/`logdata`/`tag` are static text without `%{` macros (no exfiltration). `max_action: observe` requires `pass`. Review v0 added: catch-all check against a benign corpus (one specific line per rule), Coraza-compatible argument rules (no leading/trailing space, single-space `@pm` phrases, no `%{` in operators, no escaped quotes, no backslash or comma in actions), no nested quantifiers, at most 1000 counted repetitions per pattern, `&` and `t:length` only with numeric operators, `Referer`/`Origin` only with detection operators. A seeded differential fuzz (`make contracts-fuzz`, 600,000 generated rules over three seeds, 0 disagreements after the fixes) found three RE2/Python differences that are now excluded: quantified assertions, ranges next to class escapes, repeat counts with leading zeros.

## D11 Evidence levels (G2) and rule lifetime (G8)

`evidence` carries counts (`reproduced_operators`, `sensor_operators`, `tip_issuers`, `max_issuer_share`, `human_approval_orgs`); the allowed `max_action` follows the G2 table (block: virtual patch, reproduction by 2 operators, human approval in 2 organisations; challenge: 1 reproduction or sensors of 2 operators; observe: sensors of 1 operator or tips of >= 3 issuers with no issuer above 34 %). `challenge` and `block` need `max_action_until`; challenge lasts at most 7 days. Virtual patches always have `feedback_policy: narrow_only` (G4). The claimed evidence is signed by k operators; whether it is true is the labs' responsibility (concept 21: signatures prove origin, not truth).

## D12 Client -> lab submission and ack

`POST /v0/submit` with `{request_id, envelopes[1..64]}`, at most 1 MiB. Each envelope is verified on its own. The lab answers at once with a lab-signed ack (`in_reply_to` = `request_id`, age <= 5 min) listing accepted / duplicate / rejected ids; `accepted` means durably queued, not scored (concept 21 §5). Flow control rides in `ack.control` (`retry_after_ms`, `max_batch`, `reason`); `reason != ok` requires `retry_after_ms > 0`, also with HTTP 429/503. Rejected envelopes that cannot be parsed use the id `00000000-0000-4000-8000-000000000000`.

## D13 Stream ids and resume

SSE `id` = `<relay epoch>-<seq>`. Unknown Last-Event-ID (other relay, restart, too old) triggers a full sync; because bundles are full state, the client can never miss a rule. Heartbeat every 15 s carries the newest lab-signed checkpoint; no checkpoint newer than 180 s means "frozen relay, switch". Cross-check of `/v0/checkpoint` from a second source every 15 minutes. Relay buffer 256 events per client, then disconnect. Priorities: withdrawal > bundle > checkpoint > heartbeat. ([stream.md](stream.md))

## D14 Local events

CloudEvents 1.0 structured JSON, types from concept 21 §2.1 plus `schild.rule.suspended.v1` (local brake) and `schild.signal.sent.v1` (transparency log of exactly what left the server, payload validated against the signal/feedback schema). Full visitor IP and location locally (E7). Request bodies are stored only temporarily during the request, never in events (amended by D41, E11); `query` keeps secret-looking values redacted. Incident numbers `XXXX-XXXX` from an alphabet without look-alikes. Events are unsigned local records.

## D15 Configuration

YAML 1.2 via `yaml.v3`, converted strictly (one document, string keys, no duplicates, anchors, aliases or merge keys; timestamps stay strings) to JSON, validated against the schema, then decoded strictly. Fixed safety settings are schema constants (`request_body_limit_action: reject`, `on_timeout: deny_503`, `fail_open: connection_refused_only`, `quic_0rtt: false`) so they can be documented in the file but not changed. At least two relays. Labs over HTTPS only. Retention defaults from concept 24 (raw IPs 7 days, logs 14 days / 100 MB, signals at labs <= 30 days). **OPEN**: retention of summaries (default 90 days).

## D16 Time limits

Clock skew 120 s; signal and feedback age 24 h (clients buffer while labs are down); replay window = age window; ack age 5 min; checkpoint validity 10 min; bundle validity 31 days. All timestamps UTC, whole seconds (local events may carry milliseconds).

## D17 Size limits

Signal/feedback envelope 16 KiB (payload 4 KiB), ack 64 KiB, checkpoint 16 KiB, withdrawal 64 KiB, bundle 1 MiB (payload 768 KiB), submission 1 MiB, stream event 64 KiB (inline envelope 32 KiB), local event 64 KiB, config 1 MiB, results 4 MiB, SecLang text 8 KiB.

## D18 Test keys

Nine fixed keys with public seeds `sha256("schild/testkey/v0/" + name)`, ids `test-*`, documented purposes and operators, including `lab-a2` (second lab of the same operator) and `evil` (never trusted by default). Release builds refuse them by id prefix and by public key. ([testkeys/README.md](testkeys/README.md))

## D19 Repository conventions

Ports, images, subnets (`10.66.0.0/16`, per profile and network), env vars, results path, UI embedding and the Makefile hook mechanism: [conventions.md](conventions.md). The test lab exposes dashboards only through one gateway container on a non-internal `mgmt` network; all other test networks are internal.

## D20 Dashboard APIs

OpenAPI 3.1 in [api/](api/), JSON over `/api/v0`, cookie session + CSRF header, cursor pagination (`cursor`, `limit` <= 500, `next_cursor`), RFC 9457 problem details for errors, SSE for live events. Client dashboard: full IPs locally. Lab dashboard: never IPs (labs never receive any). Fixtures use RFC 5737 / RFC 3849 addresses and RFC 5398 ASNs.

## D21 Adversarial review before the freeze (2026-10-26)

A second agent attacked the draft and fixed what it found; every finding has vectors (418 in total, Go and Python agree) and the SecLang findings were confirmed against Coraza v3.8.1.

- **SecLang bypasses (fixed).** 26 rules that the draft accepted were catch-alls, used IP/host data or diverged between parsers; in Coraza several of them block every request: `"@rx  .*"` (Coraza trims the argument), `"@pm sqlmap  nikto"` (empty phrase), `QUERY_STRING "@within abc"` (empty value), `"@rx ."`, `"@beginsWith /"`, `"@streq %{REMOTE_ADDR}"` and `"@contains %{REQUEST_HEADERS.host}"` (operator macros), `REQUEST_HEADERS:Referer "@contains shop.example"` (targets one site), nested quantifiers and 1200 counted repetitions. See seclang-subset.md.
- **Signal leaks (fixed).** The draft let an IPv4 address through as `agent.family` (`203.0.113.7`), as an integer `asn`, as a decimal or hex blob or dashed IPv6 in `action_sig`/`category`, and let a hash of anything sit in `action_sig`. `clientIp`, `X-Real-IP` and `referer` were not on the forbidden list (they still failed as `schema`). The order of `waf_rules` was a free side channel.
- **Counting (fixed).** One public key under two key ids (or labs) counted for two operators; a site key under two issuers counted twice; a signal with two site signatures had no defined issuer. Acks were not bound to the lab named in them.
- **Ambiguities closed.** Key id binding, replay window length, ASCII-only key normalisation, Coraza operator semantics for the catch-all check, client state persistence and bundle expiry behaviour are now written down.
- **Dashboard APIs.** Problem responses on every operation, cursor pagination on every list, filters on the SSE stream, no `format` keywords; checked by `contract/apispec`.
- **Known limits (accepted).** The catch-all check is a heuristic (a rule can still be broad for one kind of site; backstops: human approval in k organisations and the client's local brake). `id`, `request_sig` and the choice among valid values remain opaque channels for a malicious client (not a leak path for an honest one; `request_shape` in the local transparency log makes `request_sig` checkable). Absolute-form request targets put the host into `REQUEST_LINE`/`REQUEST_URI_RAW`; ordinary browsers do not send them, so this is no practical targeting route.
- **Toolchain (resolved by D24).** Coraza v3.7.0 and v3.8.1 (the versions in the module cache) require Go >= 1.25, while E6 fixed Go 1.24. The initiator moved E6 to Go 1.25 (D24); all modules, including the contract module, are on Go 1.25 and the client runs Coraza v3.8.1.

## D22 Addendum v0.1 (2026-10-26)

Backwards-compatible additions requested by the component teams; details in [cosign.md](cosign.md) and [CHANGELOG.md](CHANGELOG.md).

- **Co-signing on the feed port.** `GET /v0/collecting` / `POST /v0/signatures` become contract. Unpublished rule texts are not public: `/v0/collecting` needs a peer request signature. Chosen over peer mTLS because the signature reuses the keys every lab already has (`rules` purpose, configured per peer in `lab.yaml`), works through TLS-terminating proxies and is testable with golden vectors in Go and Python. Replays within the 120 s window only repeat an idempotent read.
- **Public log root = RFC 6962 MTH** over line-based leaf data (no JSON, so browser, Go and Python agree byte for byte). Fixed now so that the lab dashboard can verify the root a checkpoint signs. Inclusion/consistency proofs and witnesses stay open (open point 2).
- **Dashboard APIs.** Lab live stream at `GET /api/v0/events/stream` (same path pattern as the client's `/events/stream`; the lab's former `GET /api/v0/live` extension is removed), event name = topic, no replay (the UI refetches after reconnects). Four eyes: whoever drafted a proposal may not approve it (`self_approval`); drafts from unauthenticated localhost sessions have no named author. `Overview.series_24h` is optional so older servers stay valid.
- **Fixture naming by operationId** so the mock layer needs no mapping table.

## D23 Stage 3 preconditions (2026-10-26, initiator)

- **Kill criteria frozen.** M1–M7 and D1–D3 as written in concept 23 §2 are frozen for stage 3. Changing a threshold needs a new version of concept 23 with a reason, never after looking at live data.
- **Hard limits stay in observe mode.** Body limit (413), compressed bodies (415), more than 1000 arguments / broken or too deep JSON (400), too many or too large headers and too many cookies (400, added by D40), the limits of D41 (413, 429, 503) and the 1 s evaluation timeout (503) keep rejecting in every mode, so M1 ("never unchecked") holds. "Inspected" does not mean every byte: file content counts as not rule-inspected (D41, E4), and M1 keeps its threshold. Before schild goes in front of a live site, that site's access logs are checked for such requests and the limits are tuned per site. No "log only" mode for limits; the one exception is the minimum body rate, measured first (D41, E2).

## D25 Server check and agent (2026-10-26, initiator)

- **MVP-11 is built** (spec tests/specs/MVP-11-server-check-agent.yaml): `schild check` (read-only host findings) on the gateway and `schild agent` on every app VM behind it, including a software inventory for later advisory matching.
- **Agents report only to the gateway schild,** never to labs; signed per-agent keys with enrolment; the gateway sends no commands back. Host reports stay in the operator network and are no signals.
- **Second step, not in MVP-11:** metrics and anomalies (CPU, egress, new executables), app log events and correlation with gateway events.
- **Contracts v0.3** ([host-check.md](host-check.md), [CHANGELOG.md](CHANGELOG.md)): host report `schild.host_report/0.1` with typed evidence only and explicit forbidden content (checked before the schema: `forbidden_field`, new `forbidden_content`); agent delivery as its own DSSE kind `agent-report` (purpose `agent`, one signature, report bound to the signing key, 5 min / 120 s window, nonce, gateway name); enrolment by a self-signed request with a one-time code plus confirmation of the key fingerprint in the dashboard, or by explicit public key in `schild.yaml`; revoked keys stay on a list and yield the new code `revoked`; the gateway answers with an unsigned ack that has no field for instructions (the agent pins the gateway's TLS certificate). Chosen over mTLS client certificates because signed envelopes reuse the existing DSSE code, keys and golden-vector machinery and work through TLS-terminating proxies; over a shared secret because one leaked VM must not be able to report as another.

## D26 Withdrawing all network rules is a normal bundle (DRAFT / ENTWURF, direction decided by the initiator 2026-10-27)

Status: **draft**. Direction decided by the initiator on 2026-10-27; the contract change follows with the next free version (**v0.5**; v0.4 went to MVP-17, D29). v0 to v0.4 are unchanged. Concept: docs/concept/20 §4.5.

- The German name "Not-Aus" is dropped. Docs and UI say "Rückzug aller Netzregeln" (short "Rückzug"). Requirement ids stay (SEC-02, B10); only their titles change.
- **No separate emergency flag or message.** "Withdraw all" is an ordinary k-of-n signed full-state bundle (D04) with **zero network rules**. Same checks as every bundle: threshold of distinct operators, strictly increasing `version`, `expires`, rollback and equivocation rejection.
- **Re-enable = a new bundle** with a higher version. There is no "network off" state to clear.
- **Baseline protection always continues** (local rules, CRS, presets, hard limits); only network rules go.
- The gateway shows exactly **one state line**: `Regelstand <n> vom <Zeit>: <k> Netzregeln aktiv`, plus the reason for the current state. Proposal for v0.5: a short, static, human-readable `reason` in the bundle payload (no macros, no links, length limit); **OPEN** until v0.5.
- Unchanged: k-of-n, distribution < 10 s for 95 % (B10; a zero-rule bundle is small, always inline, highest stream priority), the local brake per rule (G8) and suspending single network rules per gateway.
- Until v0.5 the v0 `withdrawal` kind (D04) stays valid. **OPEN** for v0.5: whether single-rule withdrawals are also expressed only as a new full-state bundle without that rule, and whether the `withdrawal` kind is then removed.
- Reason: a zero-rule bundle needs no extra key purpose, code path or privilege, so SEC-02 ("a withdrawal only affects network rules") holds by construction.

## D27 Relay directory curated by labs (DRAFT / ENTWURF, direction decided by the initiator 2026-10-27)

Status: **draft**, not part of any contract version yet. **The prototype keeps the fixed relay list** in `schild.yaml` (at least two relays, D15). Concept: docs/concept/20 §4.6.

- **The operator only chooses labs.** Each lab publishes a lab-signed relay list of the relays it vouches for: URL, operator, role (`stream`; `ohttp` from v1), with `expires` and a strictly increasing version (anti-rollback, like the TUF timestamp role). It travels over the same public stream as bundles and checkpoints (working name `schild.dist.relays`).
- The gateway only considers lists signed by **its chosen labs**; lists of other labs, expired lists and older versions are rejected.
- **Labs monitor their relays** (subscribe themselves, measure lag and `seq` gaps, stale checkpoints) and drop bad relays from the next list version.
- **Gateway self-monitoring:** no fresh lab-signed checkpoint for 180 s -> switch relay (as D13); if no relay delivers, fetch directly from the chosen labs as a last resort.
- **Guardrails:** relays drawn from the lists of at least **two different labs / operators**, preferring relays endorsed by several chosen labs; the operator of each relay is disclosed (required for v1 OHTTP: the relay operator must differ from the receiving lab, E1; stream relay and OHTTP relay operators differ, concept 20 §4.3); operators may pin their own relays in addition; **no P2P discovery** for now (eclipse attacks), GossipSub only later.
- **Trust root stays local:** the choice of labs (and pinned relays) is changed only locally on the gateway, never through any dashboard, including the multi-tenant Schild Dashboard (MVP-13).
- Relays cannot alter content: bundles are DSSE with k-of-n lab signatures, checkpoints are lab-signed. A relay can only withhold, delay or observe metadata ("this server runs schild and is online"); withholding is caught by the heartbeat.

## D28 Network blocking and Spamhaus DROP by default (DRAFT / ENTWURF, decided by the initiator 2026-10-27)

- Host-wide network blocking for all ports is part of the basic protection (MVP-15, `schild-firewall`). ## D29 Behaviour across requests and rate limits (2026-10-28, initiator; MVP-17)

- **Contracts v0.4** ([CHANGELOG.md](CHANGELOG.md)): `behaviour` in `schild.yaml`, the local events `schild.behaviour.triggered.v1` and `schild.ratelimit.exceeded.v1`, and the behaviour operations of the client dashboard API. Backwards compatible; signals unchanged. The changes D26 announced for "v0.4" (zero-rule bundle `reason`, single-rule withdrawals) move to the next free version.
- **Five fixed scenarios in Go, no DSL**: `login_bruteforce`, `credential_stuffing`, `path_probing`, `aggressive_crawl`, `waf_repeat`. **Decided (initiator, 2026-10-28): the thresholds adapted from CrowdSec hub scenarios are the defaults** (MIT, attribution in `gateway/NOTICE`); testlab measurements may tune them later. CrowdSec runs nowhere and no CrowdSec IP data is used (D28).
- **Ladder per scenario**: `observe` (count, "hätte gesperrt") → `challenge` (only while the browser check of MVP-12 exists and is enabled; until then it observes, reason `challenge_unavailable`) → `block` (temporary HTTP-level block with the block page and its incident number, so the existing unblock path works). Repeat offenders escalate 15 min, 1 h, 4 h, 24 h; the cap is 24 h (schema: `duration_s` <= 86400) and every block expires by itself. Blocks live in memory: a restart ends them early, never late.
- **Who is never blocked by behaviour**: `net_class` `cgnat`, `mobile` and, decided by the initiator on 2026-10-28, `tor` (at most challenge, never a 429 from a rate limit; G1, concept 18), allowlisted own addresses and locally released senders (G6). WAF rules keep running for all of them.
- **A gateway in `mode: observe` acts on nobody** (stage 3, test profile): scenario and limit modes are capped to observe, hits record `mode: observe` with `would_action`. Confirmed by the initiator on 2026-10-28.
- **Client key**: the IPv4 address (never coarser than /24) or the IPv6 /64. Rate limits answer 429 with `Retry-After`, the calm page for browsers and RFC 9457 problem details for API clients.
- **Whole-site limits need an explicit flag** (`confirm_site_wide: true`), checked by the schema so Go and Python agree.
- **Credential stuffing without storing names**: login user names are counted with a HyperLogLog-style sketch fed by a keyed hash with a per-process random key; neither names nor hashes are stored or emitted, only the estimated count (concept 24; the spec's open question is decided for the privacy-safer option).
- **Rate limits and scenarios on the same footing**: a limit in `observe` counts "hätte begrenzt"; the CGNAT/mobile and allowlist exemptions apply to limits too (the kill criterion of MVP-17 names blocking CGNAT users).
- **Amendment (initiator, 2026-10-29): maximum block duration per net class.** Residential, mobile, cgnat, unknown and every other class except hosting keep the ladder 15 min, 1 h, 4 h, 24 h with the hard cap of 24 h (not configurable above it; cgnat, mobile and tor are still never blocked by behaviour). Data-centre addresses (`net_class` hosting) that come back may go up to 7 days: 15 min, 1 h, 24 h, 7 d (level 4 and beyond). VPN and proxy stay at 24 h (interpretation: the amendment names data centres only). Prefixes on Spamhaus DROP and similar lists (D28) stay blocked as long as they are listed (network blocking, unchanged). Blocks over 24 h are kept in `schild.db` with their expiry and reloaded at start, so a restart never ends them early; expiry is always enforced, an Art. 17 deletion removes them, and the operator's allowlisted addresses are never blocked (dropped at load and at every allowlist change). Contract: `events.schema.json` caps `duration_s` at 604800 and requires the ladder step of the level for the client's net class (vectors `events` valid 020-026, invalid 034-040); Go `events.Ladder`, `BlockDurationS`, `PersistOverS`, `ActiveBlock`; the API carries `duration_s`, `net_class` and `persisted` on blocks and the hosting ladder in `BehaviourSettings`, so the UI says how long and why ("7 Tage, weil Rechenzentrum und wiederholt").
- **Addendum (initiator, 2026-10-28):** rate limits set to `block` act from day 0; only scenarios (and the MVP-18 detectors) wait for the learning period and then record reason `learning` (contracts v0.4 addendum, D33).

## D30 Distributed attacks through residential proxies (2026-10-28, initiator; MVP-18)

- **Contracts:** v0.4 had not been released (no image, no stage-3 deployment used it), so MVP-18 extends v0.4 instead of opening v0.5. Every vector is unchanged; new vectors are appended. D26 stays planned for v0.5.
- **Count by target, fingerprint and shape; answer per route and account; never per address.** Five detectors in the MVP-17 behaviour package, responses time-boxed: `route_tighten` (until MVP-12 exists: a strict route-wide limit, 429, for requests that carry no session cookie or match a strong fingerprint of the cluster; users with a session cookie the app set pass), `account_slowdown` (wait doubling from 5 s to at most 60 s, hard cap 5 min; only for attempts without a session cookie, so an attacker cannot lock the real user out; reset by a successful login), `shape_block` (only shapes that matched WAF rules or virtual patches). Wave events are address-free.
- **Session cookie** = a cookie whose name the app itself set on this site (learned from `Set-Cookie` names, bounded), e.g. the cookie a login form sets. Chosen because it needs no app integration and a script that never loads the form does not have it.
- **Fingerprints:** JA4 only (BSD), from a configured header of a trusted TLS terminator (`fingerprint.ja4_header`, trusted proxies only), as concept 24 §10 requires; schild itself does not terminate TLS in the prototype, so neither a ClientHello nor HTTP/2 SETTINGS are available to it. Fallback: a low-entropy header set (names present, Accept/Accept-Encoding/Accept-Language shape, Sec-Fetch and client-hint presence, protocol). Header order is not available behind Go's net/http. A fingerprint is a local id (keyed per process), never stored beyond the window.
- **Learning:** a fresh installation observes at least `learning_days` (>= 14) before a detector can respond; a gateway in `mode: observe` never responds (as D29).
- **Wave hint not implemented:** signal `schild.signal/0.3` requires `waf_rules` (at least one), `action_sig`, `score` and a single `origin` and `agent` per request. A login, account, fingerprint or inconsistency wave has no matched rule and no single origin; filling those fields would misstate what happened, and the signal schema stays unchanged. `wave_hint.enabled` is a schema constant `false`. A later version may add a dedicated, IP-free hint message.

## D31 Standalone gateway as ingress (DRAFT / ENTWURF, decided by the initiator 2026-10-28; MVP-19)

- **Without the network:** a gateway may run with `network.enabled: false`: no labs, relays, signals, feedback or remote rules. The network fields are then forbidden, not ignored. Production profile without keys is valid; test keys stay refused.
- **Autoblock with local rules only:** on the initiator's own servers, `mode: autoblock` may act through CRS, local rules and exceptions, behaviour (D29) and distributed-attack responses (D30) after the learning period of at least 14 days. Partner sites in stage 3 stay observe-only until stage 4 decides; concepts 09 and 23 get a sentence on this (open, initiator).
- **schild as ingress, approach A:** `schild run` loads the operator's Caddyfile into the embedded Caddy; Caddy does TLS and ACME, schild adds the Caddyfile directive `schild` per site. This revises the MVP-16 line "no ACME inside schild": the ACME code is Caddy's, not ours. nginx setups keep `schild front`.
- **No fail-open in this setup:** schild is the ingress, so a dead process means no ingress, as with a dead Caddy today. Handler panics are recovered per request, gate timeouts answer 503. The rollback is the stock Caddy image with an empty `schild` snippet.
- **The gate stays independent of Caddy** (`internal/gate` uses plain `net/http`; the Caddy module is an adapter). Approach B, schild as an xcaddy plugin with its own Caddy app module, stays possible later without a rewrite.
- **Caddy security releases** become schild releases: CI rebuilds the image on each Caddy security release.
- **Contracts:** v0.4 is still unreleased (no tag, image or deployment uses it), so MVP-19 extends v0.4 as D30 did: `network.enabled`, `ingress.caddyfile`/`storage`/`unprotected_sites` in `schild.yaml` and `network` in the client dashboard API; every earlier vector unchanged ([CHANGELOG.md](CHANGELOG.md)). With the network off `remote_rules` and `signals` are rejected as whole sections, the stricter of the two options.

## D32 Central Schild Dashboard for own projects (DRAFT / ENTWURF, decided by the initiator 2026-10-28; MVP-20)

- **Pragmatic v1:** one central Schild Dashboard for one operator's gateways. The data model is multi-tenant from the start (tenant on every row, every query scoped); v1 runs with the single tenant `default`. Tenant UI, roles, service providers and per-admin signed actions stay in MVP-13 for later.
- **Copy allowed, bounded by the gateway:** this revises the MVP-13 line "no data copied into a parallel model beyond caching". The dashboard keeps a copy of events, changes, metrics and selected system log lines, at most as long as the gateway keeps them; IP truncation and deletions (incl. Art. 17) are mirrored within one poll. Search and charts run on the copy, never as live queries on gateways.
- **Connection in v1: SSH tunnel, no WireGuard.** The dashboard host keeps an `ssh -L` forward per gateway to the export listener on the gateway's loopback; the key on the gateway belongs to a user without shell and is restricted to that one port (`restrict,port-forwarding,permitopen=...,command=nologin`); gateway host keys are pinned. On top, one token per gateway, created and revoked only on the gateway host.
- **One action: blocking.** The dashboard and its API can only block an IP or prefix (bounded size, with expiry) and lift a block they set; no release or allow actions. Every action expires, is audited locally on the gateway and never covers the operator's own allowlisted addresses. No config, rule, mode, trust-root or attach changes from the dashboard. Blocks stay local to the chosen gateways (G1).
- **Configuration as code:** mode, scenarios, limits, exceptions and rules change only in `schild.yaml` and `rules.d` in the operator's repository and reach the gateways through the normal deployment (e.g. Kamal). The dashboard shows them read-only with a config version per gateway and may offer a change as a YAML snippet to copy, never apply it.
- **No own AI agent:** a read-only agent API and MCP server (scope `agent:read`, keyed IPs, no actions); operators connect the agent of their choice. The same read-only agent API also exists on each gateway (MVP-21, scope `agent:read`, cheap data only), so a single-server operator can connect an agent directly; the central dashboard adds the view across gateways and longer history.
- **Headless gateways:** an attached gateway may run without its built-in dashboard; the CLI stays for local operation.

## D33 Traffic and server monitoring in the gateway dashboard (DRAFT / ENTWURF, 2026-10-28; MVP-21)

- **Contracts:** v0.4 is still unreleased and the MVP-20 contracts (planned v0.5) are not written, so MVP-21 extends v0.4 as D30 and D31 did; every earlier vector unchanged ([CHANGELOG.md](CHANGELOG.md)). MVP-20 builds its export on `MetricBucket` instead of a second metric sample schema; its own 30 s sampler is replaced by the MVP-21 rings.
- **Count every request, not the events:** counters live in the gate (`finish`) and cover every request that reaches the schild handler; the sampled events stay a sample for the event list. Exact: all counts, status classes, upstream errors, body bytes, the breakdowns by country, net class, UA class, method, status class and site, kernel values. Estimates (marked, with `error_bound` or `error`): latency quantiles (bucket upper bound, at most +25 %), top paths and ASNs (space-saving, K = 64 per bucket), unique and new clients (HyperLogLog ±3.3 %, 7-day in-memory Bloom filters).
- **Separate file, fixed rings:** `<storage.path>/metrics.db` (SQLite, already a dependency) with one WITHOUT ROWID table per ring, slot = (unix / step) mod slots. Chosen over tables in `schild.db` for its own write lock (never delays the event writer), its own size outside `retention.max_size_mb` (whose cap deletes events), a fixed size and a clean reset. Resolutions fixed at 10 s, 1 min, 10 min; only their length is configurable (`monitoring.keep`, coarse never shorter than fine). Aggregation happens in memory; queries are primary-key ranges with at most 1000 points.
- **Aggregates only:** no IP address, client key, keyed hash, sketch register or filter is written or returned; IP top lists stay in the event views (E7). The keyed hash for client counts uses a per-process key held in memory.
- **Host numbers from /proc and /sys, honest about scope:** in a container /proc/stat, meminfo, loadavg and diskstats are host-wide (scope host) and the cgroup v2 limits of schild's container are shown next to them; network, sockets and conntrack are the server's only with `network_mode: host`. What cannot be read is null with a reason, never an error.
- **Hints, not alarms:** 20 fixed hint codes with fixed thresholds and the levels info, notice, warning; German text by code in the UI. Configurable thresholds are an open question.
- **Agent API on the gateway (initiator, 2026-10-28):** a narrow read-only API for agents (`gateway-agent.openapi.yaml`, agent/v0) and MCP over streamable HTTP at /mcp, both on a dedicated loopback listener (`agent_api.listen`, default 127.0.0.1:8789, off by default) reached through an SSH tunnel. A dedicated listener rather than a prefix on the dashboard listener: bearer tokens and session cookies never share a port, it runs on headless gateways, an agent's SSH key can be limited to this one port, and MVP-20's export joins it as scope `export:read`. Tokens only from the host CLI, hashed, expiring (at most 365 days); GET only, everything else 403. Monitoring, status, events and incidents by id or bounded window (24 h, 7 d) with cursor, no free-text search, caps on rows, scanned rows and bytes, rate and concurrency per token, local call log. IPs only as keyed pseudonym and /24 or /48; visitor text marked `x-untrusted`, escaped and capped. No `schild mcp` stdio command (it would need a shell for the agent user).
- **Addendum (initiator, 2026-10-28):** `waf.max_concurrent_evals` and `waf.queue_wait_ms` in `schild.yaml` (the environment variables stay as test lab overrides); behaviour reason `learning` for scenarios in their learning period.
- **MVP-22 addendum (initiator, 2026-10-29; still v0.4):** the aggregate part of MVP-22 lives in the MVP-21 rings: breakdowns by referrer domain (own sites `_intern`, known AI assistants grouped as `ai:<assistant>`, never a path, query or IP address), browser family, OS family, device class and bot category (fixed enums, no versions; bot category from the user agent, verification only with MVP-22), the counters `page_views` and `detections`, and detections per path template and per rule id as top lists, so alert rates per page and per rule cover the whole 10 min ring. The `waf.max_concurrent_evals` text now describes the cost classes of MVP-19 fix round 2.
- **D29 addendum (initiator, 2026-10-28, no contract change):** rate limits set to `block` act from day 0 and do not wait for the learning period; only behaviour scenarios (MVP-17) and distributed detectors (MVP-18) observe during it. The events schema rejects reason `learning` on `schild.ratelimit.exceeded.v1`.

## D34 Autonomous admin agent (DRAFT / ENTWURF, direction decided by the initiator 2026-10-28; later spec)

- **Goal:** an agent of the operator's choice (e.g. Hermes) runs 24/7, holds a list of the operator's gateways (reachable e.g. over a self-hosted NetBird mesh), monitors them like an admin, checks logs, verifies addresses and waves, and blocks. The operator watches the central Schild Dashboard. Schild covers security and monitoring only; deployment, updates and backups belong to other modules.
- **Prepared now in MVP-20:** a pluggable transport (SSH tunnel in v1, a mesh later) and blocking by evidence: the caller names event ids, the gateway blocks the client address it recorded for them. Addresses are resolved on the gateway, never taken from text, so injected IPs in paths or user agents cannot be blocked and an agent needs no full IPs.
- **Amended by D42 (initiator, 2026-10-30):** the condition that agents act only after a measured precision, and with it the shadow start, no longer applies to `blocks:write`. The rest of this decision stands for a later `agent:act`.
- **Later (own spec; D42 already allows single blocks by a token a person created):** a scope `agent:act` with server-enforced limits: blocking only, by evidence only, short expiry (e.g. at most 24 h), prefix at most /24 or /48, a budget per hour, never the operator's allowlisted addresses, never cgnat, mobile or tor (a human confirms those), every agent action marked in the dashboard with one-click undo, a kill switch per token. It starts in shadow mode ("würde sperren"); `agent:act` is switched on only after measured precision meets a kill criterion the initiator sets.
- **Verification uses local data only** (ASN, country, net class, the gateway's verified-bot check, behaviour across the operator's gateways). Lookups at third parties (whois, reputation services) would send addresses out and need their own decision and privacy review.

## D35 Requests, bots and geo enrichment (2026-10-29, initiator; MVP-22; contracts v0.5)

Status: contracts written (v0.5); MVP-22 itself is a draft and not built. Spec [../specs/MVP-22-requests-and-bots.yaml](../tests/specs/MVP-22-requests-and-bots.yaml).

- **Contracts v0.5:** MVP-22 opens v0.5 as a backwards compatible addendum: every v0 to v0.4 vector is unchanged and the new vectors are appended. The aggregate part (referrer, browser, OS, device, bot category, rule breakdowns, `page_views`, `detections`) went into the still unreleased v0.4 as the MVP-21 addendum (D33). D26 and the MVP-20 contracts, planned as v0.5 earlier, join v0.5 later as further addenda while it is unreleased, as D30, D31 and D33 did for v0.4.
- **Purpose (question 1):** operational statistics for security and monitoring only (concept 24, new V13 "Betriebsstatistik"). No marketing analytics: no UTM, campaigns, goals or funnels. TDDDG section 25 is not touched: no cookie, no script, nothing read from the device, client hints never requested.
- **Request ring:** `monitoring.requests` in `schild.yaml` (`enabled`, default on while monitoring is on, and a `config` error when switched on while monitoring is off; `keep_hours` 1..48, default 48; `max_size_mb` 16..4096, default 512). Append-only 10 min segment files under the storage path, retention deletes whole files; nothing in `schild.db` or `metrics.db`. A record (`RequestRecord`) has time, site, host, path, method, status, outcome (`passed`, `would_block`, `blocked_waf`, `blocked_behaviour`, `rate_limited`, `rejected_limit`, `fail_closed`), anomaly score, up to 3 rule ids, the event id when one was written, country, ASN, net class, browser/OS/device class, bot id, category and verification state, referrer key, duration on the exp1.25 scale, response bytes, a page view flag and the visitor key. Valid requests and WAF alerts are one stream and join their event without a second lookup.
- **Real paths (question 2, taken back by D63: real paths always, no switch):** path templates by default; `monitoring.requests.raw_paths` lists the sites whose records keep the real path, redacted like events and never with a query string. Interpretation of "switch per site": a list of site host names (wildcard `*.example.org` allowed), empty by default.
- **Cap and sampling (question 6):** above `max_size_mb` the ring keeps a consistent sample by visitor key (every request of a sampled visitor, none of the others); the rate is stored per segment and returned as `sample_rate`, the UI shows "Näherungswert". Numbers on the dashboard always come from the monitoring counters; the ring serves drill-down, filters and context.
- **Visitor key (question 7):** `v1-` + 8 bytes of HMAC-SHA256 over the client key (IPv4 address, IPv6 /64) with a random key that lives in memory only and is replaced at 00:00 UTC and at every start. It links the requests of one client within one day, never across days. The agent API re-keys it as a `p1-` pseudonym (`agentapi.VisitorPseudonym`, own HMAC domain, gateway-local key); it is not the `client_pseudonym` of events, which stays linked through the event id.
- **Context:** `getRequestContext(event_id)` returns the requests of the same visitor 5 min before and after the event in order and a site-wide 10 s strip of the same window from the monitoring ring; incidents and false-positive hints pin that window unsampled. Dashboard queries: one at a time, at most 6 h per query, 100000 records read; agent queries at most 1 h and 10000 records.

The spec says "YAML snippet"; local exceptions are SecLang rules in `rules.d`, so the contract offers SecLang with the suggested file.
- **Bots (questions 3, 4, 5):** a catalogue (`bot-catalogue.schema.json`, `schild.bot_catalogue/0.1`) with id, operator, category (11 fixed), robots token, User-Agent tokens and the verification method, plus range snapshots of the operators, ships with every release (and the signed rule bundle, see open point below), seeded from ai.robots.txt (MIT, attribution) plus own entries. Matching and verification are fixed in `contract/bots` and the Python cross-check: longest ASCII case-insensitive token in the first 512 bytes; otherwise `likely_automated` or `likely_browser`. Verification states `verified`, `claimed`, `mismatch` (fresh ranges published, address outside: "gibt sich als ... aus"), `unknown_stale` (snapshot older than 30 days, also for an address inside it). `bots.verify.ranges` (default on, local), `bots.verify.fcrdns` (default off: it sends client addresses to the resolver; shared with MVP-12), `bots.ranges_fetch` (default off). - **Geo (BYOK, decided earlier on 2026-10-29):** `geo.provider` `dbip` (default, bundled DB-IP Lite), `ipinfo` or `maxmind`; `token_file` or `SCHILD_GEO_TOKEN`, never in `schild.yaml` (the schema has no token key), never logged or returned; `database` (provider database ids, defaults ipinfo_lite and GeoLite2-Country + GeoLite2-ASN) and `refresh_hours` (1..168, default 24) only with a downloading provider. The field mapping per provider, including the optional `is_vpn`, `is_proxy`, `is_tor`, `is_hosting`, `is_mobile` and `carrier` and the derived net class, is fixed in `contract/geo` and the geo-map vectors. Live per-request lookups and anything below country stay out (question 9).
- **Central dashboard (question 8):** no bulk export of the ring. MVP-20 asks for bounded context through the agent operations `queryRequests`, `getRequestContext` and `getBotOverview` (MCP tools `schild_requests`, `schild_request_context`, `schild_bots`).
- **Open:** (a) carriage of the catalogue and range snapshots in the signed rule bundle needs a bundle format change; it is left for the D26 bundle work in v0.5, until then they ship with releases (and the optional direct fetch). (b) The field names of the paid IPinfo tiers (`is_vpn` or `vpn`, `carrier_name` or `carrier.name`) follow the documented MMDB layouts as far as known; the measurement with real test databases (spec MVP-22 `measure`) confirms them, a difference is a contract change.

## D36 Website-first dashboard (2026-10-29, initiator; contracts v0.5)

Status: contracts written (v0.5, unreleased, backwards compatible); UI and gateway not built. Trigger: the MVP-21 Überblick mixed traffic of all domains, host CPU and disk, lab recommendations and network rules ("alles Chaos"). Users think in websites, not servers; one website may run on several servers, and the typical setup is several apps on one server.

- **Information architecture (what the APIs serve):** start page "Websites" (one card per website: status, requests per second, share stopped, response time p95, "läuft auf N Servern"); one website with the tabs Überblick, Zugriffe (MVP-22), Angriffe, Ausnahmen, everything filtered to it and "Läuft auf: <server>"; "Server" as a separate infrastructure area; navigation Websites, Server, Einstellungen. Network pages (Regeln, Freigaben, Signale) disappear with the network off and move under Einstellungen → Verbund with it on. A server problem reaches its websites only as a short hint ("web-1: Platte fast voll").
- **What a website is** (`contract/websites.Derive`, vectors `website-derive`): in ingress mode one Caddyfile site block is one website with all its addresses (http and https, every port and path); blocks that share a host after normalisation are one website (union over shared hosts, so `http://example.org` and `example.org:8443` never become two cards). A block counts when it runs schild, or proxies and all its hosts are in `ingress.unprotected_sites` (protection `unprotected`, listed without numbers; mixed: `partial`); redirect, static and probe blocks without schild are no websites; a block that proxies without schild and is not listed is a `config` error (the MVP-19 validator). In proxy mode there is one website, named after the first of the new key `upstream.site_hosts`, else `default`. MVP-16 `sites`, once contracted, will name proxy-mode websites explicitly.
- **Website id:** the first host of the earliest block (host-less addresses only when there is no host): one trailing dot removed, ASCII lower case, non-ASCII labels as Punycode A-labels (RFC 3492, no further IDNA mapping; upper-case non-ASCII letters are refused so every implementation agrees), no port; a wildcard label becomes `_` (`_.example.org`), IPv4 literals as is, IPv6 as `ipv6-` + RFC 5952 form with `-` for `:`, host-less blocks `_any`. Stable as long as the first host stays the first host. `default` is local to its gateway and never merged across gateways. The label shows Unicode. The existing cap stays: the first 32 websites schild sees have their own series, the rest is `_other` (an unprotected website takes no place).
- **Request → website** (`Set.Resolve`): exact host, else the matching wildcard with the fewest `*` labels, else `_any`, else none; proxy mode: always the one website. This is how events, incidents, behaviour hits and waves get their website for the `site` filter.
- **Status** (`contract/websites.Status`, vectors `website-status`), over the last 5 minutes, deciding reasons first: **gestört** (`disrupted`) when every gateway the website runs on is down (gate not ready, Grundschutz off, or for MVP-20 unreachable), or at least 10 requests and >= 5 % answered 503 by schild (`fail_closed`), >= 20 % of forwarded requests without an answer or timed out (`upstream_unreachable`), or >= 20 % 5xx (`errors_5xx`); **bitte ansehen** (`attention`) for any website hint, any hint of a server it runs on (every level, as decided), a degraded Grundschutz, or some (not all) of its gateways down; **keine Messwerte** (`unknown`) for unprotected websites and without numbers (monitoring off, untracked, no data yet); **ok** otherwise, also with no traffic. ## D38 Storage bounds and log hygiene (2026-10-29, initiator; contracts v0.5)

Status: contracts written (v0.5, unreleased, backwards compatible); gateway, host check and UI not built. Trigger: the read-only audit `tests/results/storage-bounds-audit-2026-10-29.md` asked whether schild can fill a disk by itself. Mostly bounded, with four real gaps: the `schild.db` size cap ran only every 10 minutes, deleted only events (incidents and signals could keep the file above the cap after every event was gone), deleted oldest first regardless of value, and process logs had no rate limit. The initiator approved all eight fixes. Rules in [storage-bounds.md](storage-bounds.md), Go `contract/storage`, vectors `storage-bounds`.

- **Size cap by bytes and time:** a pass runs at start, every 600 s and as soon as the writers wrote a tenth of `retention.max_size_mb` (N = 10 % of the cap). Used bytes include the WAL; `journal_size_limit` 64 MiB on `schild.db` and `metrics.db`, `wal_checkpoint(TRUNCATE)` before and after each pass. Guarantee: at most one check step (10 %) plus one batch above the cap between passes.
- **Everything that grows with traffic is inside the cap:** events, incidents, signals and deliveries, the agent call log.
- **Deletion by value**, vector-tested: the agent call log is trimmed to its newer half first (no longer wiped), then sampled requests → logged (passed, logged, flagged sessions, anomalies) → would_block (incl. observing behaviour and rate-limit events) → blocked (incl. enforced ones) → incidents → records (waves, rule and config changes, unblocks, environment, advisories, dashboard resets) → `signal.sent` and the transparency log last; oldest first within a class, down to 95 % of the cap. The newest 100 rows of each class are never deleted by the cap (only by age), so a flood of one kind never empties another ("a flood of incidents never leaves 0 events").
- **When the cap cannot be reached** (every class at its floor): the pass stops, the gateway raises the new hint `store_cap_unreachable` (warning) and logs one warning per hour at most, instead of deleting everything.
- **Disk budget:** budget = cap + 10 % + 2 × 64 MiB WAL + `metrics.db` bound + request ring cap. Larger than the file system of `storage.path`: preflight refuses to start (`config`, `/retention/max_size_mb`). Growing to it would leave less than max(1 GiB, 5 % of the file system) available: new hint `storage_budget` (notice). Thresholds fixed in v0.5 like the other hint thresholds.
- **Incident aggregation per client, rule and minute:** WAF and request-limit blocks of one behaviour client key, one rule key (sorted rule ids, or `limit:<code>`) and one UTC minute are one incident with `count`, `first_seen`, `last_seen`. The incident number semantics of the block page stay: the first request draws the number, every later request of the aggregate shows the same number and its event carries it, so a reported number always finds its incident (`IncidentNumber`, `Incident.count`, `AgentIncident.count`). At most 65 536 open aggregates; beyond that a request gets a single-request incident (never dropped). Behaviour and rate-limit blocks keep one incident per block.
- **Small tables:** expired `kept_blocks`, `review` and allowlist rows are deleted by every pass; a long block evicted from memory is deleted from `kept_blocks`; ended behaviour blocks are evicted before running ones.
- **Process logs:** every per-event warning is rate-limited per message (first occurrence, then at most one line per minute with the number suppressed). Documented behaviour, not a contract type. Runbook and compose example set Docker `max-size: 10m`, `max-file: 5`.
- **Caddy logs:** `schild ingress validate` warns with code `log_roll_disabled` (message key `ingress.warn.log_roll_disabled`) for every `output file` with `roll_disabled` (the embedded Caddy does not reopen the file, so the logrotate rule needs `copytruncate`).
- **MVP-20 and MVP-22 specs:** the central copy gets its own size cap and propagates deletions caused by the gateway's size cap; metric and system-log copies have a retention; pinned context segments of the request ring count against `keep_hours` and `max_size_mb`; a geo download keeps only the last good database and removes its temp files (spec notes, no wire change yet).
- **Log hygiene on the host (MVP-11 addendum "Log-Hygiene", read only):** new host-check area `logs` with findings `logs.docker_unbounded`, `logs.journald_size`, `logs.logrotate_missing`, `logs.logrotate_stale`, `logs.logrotate_config`, `logs.large_file`; evidence `size_bytes`, `growth_bytes_per_day`, `fs_percent`, `mount`. Fixes that are config files use the new typed **`fix_config {path, content}`**, rendered only from gateway-side templates whose variable parts are checked paths, slugs and numbers ([host-check.md](host-check.md) section 2); a report with any other fix_config is rejected (`schema`), so an agent cannot show arbitrary file content as a fix. Detection, rights, false-positive rules, severities, texts and must/measure/kill_if in [specs/MVP-11](../tests/specs/MVP-11-server-check-agent.yaml).
- **MVP-21 hint `disk_fill_projection`:** from the existing 10-minute ring only; Theil-Sen slope of the daily minima of the last 7 complete UTC days (days with at least 36 points, at least 4 days), steady growth required (two thirds of the steps rise, so a one-off copy or a sawtooth gives no hint); notice under 14 days left, warning under 3. Reaches every website on the server like `disk_full_soon`.
- **MVP-09 addendum `schild dashboard reset-password`:** the audit entry is the new local event `schild.dashboard.access_reset.v1` (`via` host_cli or control_path, `users_removed`, `sessions_ended`, optional `host_user`; never a password, hash, setup code or session id). Value class record for the size cap.
- **Website status:** `store_near_cap`, `store_cap_unreachable` and `storage_budget` mark only the server (see the D36 amendment of the same day).

- **D33 / D36 / MVP-21: minute checkpoint and gap kinds (question about SIGKILL, measurement section 4.3).** Every 60 s the gateway writes the running 10 min bucket into its slot, gateway-wide and per website with top lists and clients estimates, as a checkpoint row (`partial` true, `gap_kind` lost); the bucket's final write replaces it, an orderly shutdown writes `gap_kind` restart, and a start inside the same bucket resumes from the checkpoint (clients estimates: the checkpoint's plus the new ones, a client may count twice in that partial bucket). A hard stop therefore loses at most one minute of per-website top lists too; the meaning of `partial` is unchanged. Builder's request, accepted: optional **`gap_kind`** (`restart` | `lost`, only with `partial`; lost wins) on `KpiValue`, `TrafficBreakdown` and `MetricBucket`, so the UI tells a deploy ("Neustart") from real loss ("Messlücke"); a missing bucket between an orderly shutdown and the next start is `restart`, any other `lost`. **`BehaviourBlock.ended_at`**: set once a block is no longer in force (ran out, lifted, or ended by a restart when not persisted); clients treat a block as running exactly while it is absent (the measurement saw 15-minute blocks ended by a restart still shown as "Gesperrt" with "Freischalten").

## D39 amendment: no password, agent write, newer set wins (2026-10-30, initiator; MVP-26; contracts v0.5)

Trigger: the initiator on the password of the switch: "das wäre schlechte usability. Auch über die API muss man sperren dürfen (z.B. mit einem lokalen agent)". Second decision the same day: between the stored set and the image snapshot the newer wins. Third: the source blocks only with `state: block` and gateway mode `autoblock`. This replaces the matching bullets of D39.

- **No password on the switch.** `updateCrowdsecHub` needs session and CSRF for every transition, also to `block`; `confirm` is gone from the body. **Difference from the mode, on purpose:** changing `mode` keeps the password. The switch is meant to be quick, and a mistake is undone with one click.
- **The agent API may write, this one thing.** It was read only by contract and by design (MVP-21, D33: "nothing here writes"). `updateAgentCrowdsecHub` and the MCP tool `schild_crowdsec_hub_set` are the one exception. `apispec` names the operation, so a second write fails the test; `agentapi.WriteOperations` holds one entry (D42 adds the two block writes under their own scope). Not requested and not added: a single rule, the mode, anything else.
- **Scope `crowdsec:write`,** narrow on purpose (`agent:write` would invite more): `agent:read` plus this operation. The default of `schild token add` stays `agent:read`, and a token keeps the scope it was made with, so existing tokens stay read only. Anything else gets 403 `scope_required`, not `forbidden`, so an agent can tell the operator what is missing. A token with this scope needs `--label`, which is its name in the history.
- **Who set it:** `state_source` gains `agent`, `state_set_by` names the token. One overlay value, the last writer owns it; dashboard and agent can overrule each other, and `reset_state` works for both.
- **History:** every change of the effective state, from either side, writes `schild.rule.hub_switched.v1` and the annotation `crowdsec_hub_changed`, with the token name for an agent. Without a password this is the record of who changed protection. Each agent call stays in the call log.
- **No CSRF in the agent API:** a bearer token is not ambient, and the loopback listener, Host check and Origin refusal stay. The write adds `Content-Type: application/json`.
- **Risk accepted by the initiator:** a holder of a `crowdsec:write` token can switch these rules off or to `block`, also a compromised local agent. The agent API stays off by default and the scope is opt-in per token.
- **Blocking needs `state: block` and mode `autoblock`.** This replaces "`block` acts in `review` and `autoblock`" of D39. In `review` the source acts as `detect` with reason `gateway_review`: that mode promises that new rules take effect only after the operator agrees, and an automatic hub update must not break that. `observe`, of the gateway or a website, stays `would_block`, and settling stays. Updates arrive in every mode; the mode only changes the effect. New read fields `gateway_effect` and `limited_by` let the UI say why rules only detect while the switch shows `block`. Per-rule entries under Freigaben are a later idea, not in this contract.
- **The newer set wins at start,** whatever `auto_update` says; a pin wins over that; a set that fails to load is out, so a stored set falls back to the image. "Newer" is `Set.Time()`: new optional `hub_commit_at`, else `fetched_at` for a master set, else no date. The commit time alone would not do: the master index names no commit, and the gateway fetches only the one file. A tie and two sets without a date keep the stored set; a date beats no date; an unreadable date, or one more than 120 s ahead of the clock, is no date. `make crowdsec-snapshot` must write `hub_commit_at`. This closes the question left open in the first report.

Rules in [ingress-order.md](ingress-order.md) section 1a, vectors `ingress-order` valid 029-044. - **Too broad `ingress.trusted_proxies` (review 1.2, G5).** Until now only signals paused while the gate still believed `X-Forwarded-For`, so any client could get a victim's address blocked. Whoever holds a /48 could collect one `PerClient` share per /64 and fill every expensive slot, so one /48 together holds at most `PerClient * SharedFactor` expensive evaluations (8 by default). cgnat and mobile addresses are exempt: carriers put many people under one /48. - **Incident hits are bounded (review 2.4, D38).** The pending hits of aggregated incidents hold at most as many entries as `open` (65 536). They empty twice a second, so the bound only matters while the store stalls. A hit that does not fit, or whose row never appears, is dropped and counted (`schild_incident_hits_dropped_total`, log line); the request keeps its incident number and the row's `count` stays too low. ## D42 Agents may set and lift single blocks (2026-10-30, initiator; contracts v0.5)

Status: contracts written (v0.5, unreleased, backwards compatible); gateway and UI not built. Trigger: the initiator decided that an agent may also set single blocks. Go `contract/agentapi` (`CheckBlock`, `CheckLift`, `ProtectedAddress`), vectors `agent-block`, API [api/gateway-agent.openapi.yaml](api/gateway-agent.openapi.yaml).

- **Two writes, one new scope.** `createAgentBlock` (`POST /agent/v0/blocks`, MCP `schild_block_create`) and `liftAgentBlock` (`POST /agent/v0/incidents/{incident}/lift`, MCP `schild_block_lift`), scope `blocks:write`: everything `agent:read` may, plus these two. `crowdsec:write` and `blocks:write` do not include each other, so an agent that needs both has two tokens. The default stays `agent:read`, existing tokens keep their scope, `--label` is required (`agentapi.NeedsLabel`). `WriteOperations` now has three entries, and `apispec` still names every write.
- **What an agent names: an event, an incident or a client pseudonym, never an address.** The gateway reads the address it recorded, so text in a path or user agent can never choose a target (D34), and neither request nor answer carries an address. A pseudonym is keyed and cannot be reversed: the gateway compares it over the newest `MaxScanRows` events with a stored address. **Visitor pseudonyms of the request ring look the same but have no address behind them** (D35), so they answer 404, and the agent uses the `event_id` of the record. Evidence older than 7 days, or an address already shortened by retention, answers 409 `target_gone`. An address whose attribution is neither `tcp_peer` nor `trusted_proxy` is refused (`unreliable_attribution`): it could name a victim.
- **One client key only:** IPv4 address or IPv6 /64, as every behaviour block. No prefixes, unlike D32's planned central action.
- **How long.** `duration_s` and `reason` are required. At least 60 s, at most the cap of the net class (D29 amendment): `hosting` 7 days, everything else 24 h. **The agent chooses within the cap; there is no ladder.** Above the cap the call is refused with `duration_over_cap` and the cap, never shortened silently. Over 24 h the block is kept in `schild.db` as D29 says; shorter ones end with a restart, early and never late. A running block stands: 200, `changed: false`, its end does not move, and the budget is not touched.
- **Never blocked:** own addresses (allowlist, the addresses of the gateway host, `ingress.trusted_proxies`: blocking a proxy would block everyone behind it), private and special ranges (`ProtectedAddress`), `cgnat`, `mobile` and `tor` (D29, decision 9 of D40), and a client the operator released (a running exception from `unblockIncident`, G6: an agent does not overrule a person). An allowlist change ends running agent blocks as it ends others. A later Art. 17 deletion lifts them.
- **Verified bots can be blocked (initiator, 2026-10-30: "darf alles").** There is no refusal for a verified bot, a search engine crawler included, so `CheckBlock` does not read the verification state.
- **In seconds (initiator, 2026-10-30: "wir müssen in sekunden KI-basiert agieren können (wenn nötig)").** In `review` and `autoblock` a block is in force before the answer returns: the engine holds it in memory, the next request of that client gets the block page. Nothing waits for it: no shadow start, no precision gate, no learning period, no settling, no confirmation, no restart, no queue. Only the disk writes of event, incident and kept block are asynchronous, and a lost one never ends the block early. A request already past the check finishes. In `observe` it stays `would_block`.
- **Limits.** `agent_api.block_writes_per_hour` (default 600, 1 to 36000, per token, rolling hour, creating and lifting together; 429 `block_budget`) and `agent_api.max_agent_blocks` (default 2000 running, 1 to 4096, gateway-wide, so that many tokens do not add up; 429 `block_cap`). Only a call that changes something counts. The budget lives in memory: a restart clears it. These come on top of `requests_per_minute` (default 120), which is then what bounds a burst. **Coordinator decision, for the initiator to check:** the first draft had 30 and 500, which does not fit acting in seconds during a wave.
- **Observe mode: nothing is blocked, recommended and contracted.** In gateway mode `observe` a write answers 200 with `effect: would_block`, `limited_by: gateway_observe`, no incident; it writes `schild.block.set.v1` and counts against the budget. Reason: D29 promises that such a gateway acts on nobody, and the initiator confirmed it for stage 3; a token must not be the way around that promise. Every refusal is checked there too, so the records show what the agent would have done. Consequence: in the first live test agent blocks are dry runs. `review` does not hold a block back (that promise is about rules), and a learning period does not either (it holds detectors back, not a decision somebody made).
- **Lift only.** `liftAgentBlock` ends the block and nothing else: no exception, no allowlist entry, no feedback, and counters and ladder stay. It does not use `Engine.Release`, which resets them; the builder needs a narrower call. A false positive stays a person's decision through `unblockIncident`. Any running block can be lifted, also one a behaviour scenario set: the use is an agent that checked a block and found it wrong, the client stays under every rule, and the WAF was never touched. It does not reach network rules or single WAF refusals (409 `no_running_block`).
- **History.** Every call is in the call log with status, refused ones too. A change writes `schild.block.set.v1` or `schild.block.lifted.v1` with token id, label and reason (value class record, the name stays after a revoke), and shows as the annotations `agent_block_set` and `agent_block_lifted`. `BehaviourBlock.set_by` and `agent_reason` mark a block as set by an agent; `source` is `agent:<token id>`, `level` 1. No signal, ever: blocks stay local (G1).
- **Reason text is untrusted.** An agent may have read visitor text, so `reason` is sanitised, capped at 300 characters and rendered as text.
- **Relation to D34 and D32.** D34's condition, a shadow start and a measured precision before agents act, **does not apply to `blocks:write`** (initiator, 2026-10-30). A person creates the token for one gateway; from then on the agent acts at once in `review` and `autoblock`. D34 stays for a later `agent:act`. MVP-20's central dashboard stays as D32 says.
- **Accepted risk (initiator):** a holder of a `blocks:write` token, also a stolen one or a compromised local agent, can block visitors for up to 24 h, data-centre addresses for 7 days, verified bots included, up to the limits above, and can lift running blocks. A wrong decision of an agent takes effect in seconds, with no gate before it. The agent API stays off by default, the scope is opt-in per token, the listener is loopback, every write is recorded with the token name, and the operator can lift each block.

## D43 Fix round after the independent measurement of MVP-26 and D40 (DRAFT / ENTWURF, for the initiator; contracts v0.5)

Trigger: `tests/results/MVP-26-messung-2026-10-30.md`. Backwards compatible: v0.5 stays unreleased, the generator appends, earlier vectors keep their results. Rules in [crowdsec-hub.md](crowdsec-hub.md) and [ingress-order.md](ingress-order.md).

- **Measured cost of a whole hub set (finding 1).** Before a set with new or changed rules goes live, a fixed probe set of six requests runs on three instances without the CRS: no hub rules, the image snapshot, the candidate. The candidate may add at most 4 times what the snapshot adds, refusal `set_too_costly`. Relative on purpose: all numbers come from one machine at one moment, so a slow or busy machine does not refuse a normal set. Fastest time of 16 rounds, so disturbance falls away. The mark is the snapshot, never the running set, so a hostile index cannot raise it in steps. The floor of two baselines covers a tiny or missing snapshot. Why 4: the snapshot adds 72 µs here, so about 290 µs are allowed, which is +9 % on the 3.23 ms of the replay mix; a real hub of twice the size stays inside, and ten hostile rules on top are at ratio 21. It runs in the update's goroutine with pauses, holds no slot, ends after 15 s, and early for a set twice over the bound. Verdict in the vectors (op `set_cost`), timing Go only. Memory is bounded by the static bounds, not measured.
- **Static bounds tightened (finding 1).** 500 rules (from 1000, today 206), 1 MiB of SecLang (from 8 MiB, today 64 KiB), new 2000 SecRule lines (today 487, code `set_too_large`). They stop the measured shape before anything compiles, and leave the hub room for about four times today's size. When the hub outgrows them, updates are refused calmly and the running set stays until a new image.
- **`shrink` compares with the image snapshot (finding 2).** A running set that grew too large blocked every normal index, and a running set that shrank would have lowered the mark for a walk down in steps. The cost: a hub that really removes more than half of what the image shipped is refused until the next image or a pin, and a set can lose up to the part above half the snapshot in one update.
- **A pin wins (finding 2).** A pin skips `shrink`: the operator named the commit. The cost check stays.
- **Reset (finding 2).** `resetCrowdsecHub` (`POST /rules/crowdsec-hub/reset`, session and CSRF, no password, as the switch) and `schild crowdsec reset` drop the stored row and run the snapshot without a restart. Event `schild.rule.hub_updated.v1` gains outcome `reset`. The control path gains its second operation. Not in the agent API: its one write stays the switch.
- **`off` keeps the stored set (finding 2).** It unloads and stops the fetch, nothing else. A switch back loads what a start would load. `off` is no way back from a bad set; the reset is.
- **Stored rows carry `cost_checked`.** A row without it, or above the new bounds, does not load, so a hostile set stored before this round heals with the upgrade. The cost: on the first start after the upgrade a gateway runs the image until the next accepted update, and rules newer than the image settle again.
- **Share of an IPv6 /48 (finding 3, replaces the number in D40).** `min(MaxHeavy, PerClient * SharedFactor)` equalled `MaxHeavy` for every slot count from 2 to 1024, because `PerClient` is `max(2, MaxHeavy/3)`. With 2 expensive slots (4 evaluation slots) a /48 gets 1, one less than an IPv4 client, and with one expensive slot there is nothing to divide. cgnat and mobile addresses stay exempt, and cheap requests are not touched. `SharedFactor` stays for the share of one cgnat or mobile address, where it does not bind either (open below).

This may break a backend that needs another upgrade (none known for Laravel or WordPress). WebSocket has the same tunnel character: the handshake goes through the rules like any request, the frames do not. Kept because Livewire and Reverb can need it.

Variables never count as server-side, also `client_ip`: `vars` can overwrite them.

- **Unblock frees the client (finding 6).** An exception holds for the IPv4 address or the IPv6 /64, as incidents and blocks do. An incident folds a whole /64, and its unblock freed only the address of the first request.
- **Text corrected (finding 6):** crowdsec-hub.md section 3 on plain text bodies with the CRS.

## D44 Bodies waiting for the backend, and the multipart class (DRAFT / ENTWURF, for the initiator; contracts v0.5)

Trigger: the independent measurement before the first live test, findings 1 and 2. Backwards compatible: v0.5 stays unreleased, the new keys are optional, the generator appends and earlier vectors keep their results. Rules in [body-limits.md](body-limits.md) sections 1 to 3.

- **Where the memory went (heap profile, 2 GiB, 2 CPUs).** 600 waiting bodies of 1 MB: 642 of 784 MiB in `io.ReadAll`, the copy made so the transaction could close. 3000 waiting bodies of 1 KB: about 105 KiB each, 12,000 goroutines (four per request), 102 MiB of stacks. So the copy is the defect, and the overhead is the part a limit on bytes of body alone would miss.
- **A checked body leaves its transaction at every size.** Up to 128 KiB it waits in memory, above that in a temp file of its own. The limit of 1 MiB (`earlyCloseBody`) is gone: bodies above it kept their whole transaction open through the wait, with every transformed value and the text body as a string, and that memory was counted nowhere either. The cost: a second disk write per forwarded body over 128 KiB, and Coraza's file exists beside it for that moment.
- **Held bytes last until the request ended,** not until the transaction closed. This changes D41's reading "until the transaction closed", which left the wait uncounted.
- **Waiting bytes are a new account, not a higher count of bodies.** D41's `max_per_client` 8 could not simply last until the answer: a Livewire page or an office would hit it at once behind any slow app. Bytes also work for every size: 128 KiB of overhead per waiting request, plus the body in memory. Defaults: 64 MiB per client, about 250 to 500 requests; 256 MiB per network; a quarter of the memory for the gateway, 512 MiB at 2 GiB. Factor 4 for `cgnat` and `mobile`, as D41.
- **Why these numbers.** A quarter of the memory leaves the parked bodies of D41 (up to 800 MiB at 2 GiB), the evaluations and the base of the process inside the Go limit of 1.75 GiB. Per client: 60 requests per second behind one address, waiting 3 s each, are 180 requests, about 25 MiB. At 10 s that is 600 requests and over the share, but then the application has long run out of workers.
- **The Go limit gives way to socket memory.** Waiting bytes alone did not hold: fast senders from many networks filled the socket buffers of 1024 bodies being read, up to 552 MiB, and the container was killed at 154 MiB of waiting bytes. The live heap was 464 MiB. The kernel charges socket buffers to the container, the Go runtime does not know them, so the collector saw room that was gone. `schild run` now takes the `sock` line of `memory.stat` off the Go limit once per second, down to half of it, in a container without an operator's `GOMEMLIMIT`. No contract: it changes no answer and no key. The collector works harder only while sockets are full.
- **Answer.** `body_waiting_share`: 429 with `Retry-After` 5 to 8, for `cgnat`, `mobile`, `tor` 503 with the waiting page, no incident, event sampled, `schild_bodies_aborted_total{reason="waiting"}`. Gateway-wide `body_busy`. A code of its own, because the cause differs from `body_client_share`: the backend is slow, not the client greedy. Checked at admission, before any WAF work, and never against a body that passed its evaluation: an overshoot of a few hundred KiB is cheaper than throwing away finished work.
- **`multipart` means `multipart/form-data` on one header.** Every other subtype is raw: it loses the file estimate and meets the raw limit. A header sent twice is raw too: rules read every value, the parser the first, and a second `application/json` switches Coraza to another parser than the first value names. Coraza's prefix test stays wider than the class on purpose. Cost: a batch API on `multipart/mixed` above 128 KiB gets 413 until the operator raises `raw_body_limit_bytes`.
- **Open for the initiator.** The three defaults (E6 applies: check them with real numbers in week 1). Whether requests without a body count too: a GET waiting for a slow backend costs the same memory, and D44 does not bound it. A share of held bytes per client, because one address can still fill the disk budget with bodies above 128 KiB.

## D45 Requests waiting for the backend, large bodies, memory pressure, a stalled body (DRAFT / ENTWURF, for the initiator; contracts v0.5)

Trigger: the third independent measurement before the first live test. Its attack parameters stay on its own branch, so this entry names causes and limits, not recipes. Backwards compatible for everything served: v0.5 stays unreleased, the new keys are optional and the generator appends. **Two D44 vectors changed** (`waiting-over-memory-limit`, `waiting-megabyte`), because a body on disk now counts its send queue, see below. Rules in [body-limits.md](body-limits.md) sections 1, 2, 2a, 2b and 4.

- **Requests without a body had no limit at all.** D44 left this open. A running request costs about 100 KiB of live memory with or without a body, 150 to 200 KiB of the container with the collector's margin, and nothing warned before the kernel killed the container. Now every request counts from its admission until it ended, per client, per network and for the gateway, in every mode. The admission comes before any WAF work and before `bypass_waf`: an allowlist entry says who is trusted, not how much memory there is. Nested evaluations hold one place (D33). `schild_requests_waiting` shows the count.
- **Defaults (E6 applies: check them with real numbers in week 1).** `waf.requests.max_waiting_per_client` 1024, `max_waiting_per_network` 4096, `max_waiting` half of the memory at 128 KiB each, so 8192 at 2 GiB. Factor 4 for `cgnat` and `mobile`, as D41. A page of 100 assets over HTTP/2 is 100 requests, so ten browsers fit behind one address at the same moment; 40 requests per second without a body with a backend of 25 s fit too (corrected by D46: with a body the waiting bytes of D44 bind first, at about 512 requests, so after about 13 s at that rate). Above that a backend has run out of workers anyway. The limit is on requests, not connections, because one HTTP/2 connection carries many. Why a count and not waiting bytes: D44's 64 MiB would be 512 requests for a client, which an office with a slow app reaches.
- **Answers as D44.** `request_waiting_share`: 429 with `Retry-After` 5 to 8, for `cgnat`, `mobile`, `tor` 503 with the waiting page. Gateway-wide `request_busy`, 503. No incident, event sampled. `fail_closed_by.body_busy` and the waiting page reason `body_busy` cover these too, so no new counter in the monitoring codec and no UI change: the class says the gateway took no more on, the limit code says which limit.
- **A full gateway answers everybody with the waiting page.** A flood from many networks that fills `max_waiting` keeps the container alive, not the site: visitors get 503 while it lasts. Before they got 200 until the kernel killed everything. A lower limit would make this easier to reach, a higher one leaves less room for bodies.
- **WebSockets and event streams count for as long as they run,** because they cost the same. A site with thousands of open sockets raises `max_waiting`.
- **Where the memory of large bodies went (heap profile, `memory.stat`, `/proc/net/tcp`, 2 GiB, 2 CPUs).** Not into the heap alone. Peak of a run that was killed: anon 1043, sock 669, dirty 302 MiB, together over the limit within seconds. Live heap in the read phase about 700 MiB, with garbage and free spans up to 1.5 GiB. Each body over 128 KiB lies on disk up to three times (Coraza's buffer, its multipart file, the waiting file), and dirty pages count against the container until they are written. Socket memory: about 335 KiB per backend socket in the send queue while the backend reads nothing, 420 MiB in all, and 450 MiB in the receive queues of refused connections in `FIN_WAIT2`, where net/http half-closes and waits 500 ms while the sender goes on. What did not help, measured: capping `tcp_rmem` and `tcp_wmem`, and pausing reads under pressure. Those are not in this round.
- **`max_large_in_flight`, new.** D41's `max_in_flight` of 512 per GiB fits small bodies. A body declared over 128 KiB, or of unknown length, costs far more while it is read, so these have a limit of their own: 128 per GiB, 256 at 2 GiB. Over it: `body_busy`. Small forms are not touched. **The cost:** slow uploads from eight networks fill it, and other large uploads get 503 until the minimum rate is enforced.
- **A body on disk counts its send queue.** `Waiting` is now the overhead plus at most 384 KiB of the body, so up to 512 KiB. D44's 128 KiB undercounted by a factor of three to four, which is why `max_waiting_bytes` never bound. At 512 MiB that is about 1000 waiting large bodies on the gateway, 128 per client.
- **Memory pressure, new.** Admission counts what it knows, the kernel kills on what it sees. `schild run` reads `memory.stat` five times per second (it was once per second, for sockets only). Held memory is `anon + sock + file_dirty + file_writeback`. From 70 % of the container limit new bodies get `body_busy`, a refused body is not drained and on HTTP/1 its connection closes at once, without the half-close; the Go heap goes back to the kernel at most every 2 s. From 85 % new requests get `request_busy`. `schild_memory_pressure` shows the level. **The cost:** a client may lose the answer to a reset under pressure. It needs a limit from the cgroup, so beside an operator's `GOMEMLIMIT` or outside a container it does nothing.
- **No real bound for the sum at 2 GiB, said plainly.** Requests, large bodies and waiting bytes are bound now, each on its own. Their sum, the socket memory of open connections and dirty pages are not: nothing here limits connections, and the brake only stops what comes in. In the builder's runs held memory peaked between 67 and 91 % of the limit, so the margin at 2 GiB is about 180 MiB in the worst run. Whether that holds on another kernel, disk and network is not shown.
- **A stall is no attack (finding 3, E10).** A read timeout of the server (`read_body`, `read_body_idle`, 1 minute by default in Caddy 2.11) counts as `client_gone` in every mode: no incident, no event, only the counter (op `read_end`). This takes back D41's "every other read error stays `body_read_error`" for timeouts. The stalled client still reads a 400 without a page. The request stays `blocked` in `schild_requests_total` and in the hourly summary, as every `client_gone` does; only the incident and the event are gone.
- **431 stays invisible (finding 4).** There is no hook without a fork. On HTTP/1 net/http writes the 431 straight to the connection in its read loop. On HTTP/2 a truncated header list goes to an internal handler; neither reaches Caddy's handler chain, `ErrorLog` or the access log, and `HTTP2Config.CountError` does not fire for it. Caddy's one hook, `listener_wrappers`, sees HTTP/1 on a plain port before TLS; after TLS it takes connections off the `*tls.Conn` path of every site, and on HTTP/2 the status lies in HPACK. Not worth that for a low finding. The runbook now gives the real limit: Caddy's 16 KiB, not 64 KiB.
- **Lift right after a set (flaky `TestAgentLift`, `TestAgentBlockThroughMCP`): a real race.** The row of a block is queued, the block runs at once. A lift within that gap answered 404 for a running block, and if the row came after the block's end was written, it stayed `blocked` for good. Now a lift that finds no row but a running block has the row written first (at most 2 s), and lifts without one if it never comes. Real agents would have hit this.
- **Proposal, not changed:** `waf.body.max_per_client` 16 and `max_per_network` 64 (today 8 and 32). The measurement found no price and offices stop failing up to 16 uploads. They do not touch the OOM. The initiator decides.
- **Builder's check, no measurement (arm64, Docker Desktop, shared machine under load, a backend that holds requests and reads no body; the builder does not measure its own work).** Requests from one address stayed at a sixth of the memory that killed the container, and many networks at a full gateway at about 1.3 GiB. Bodies from many networks and the mix with requests: no kill in 21 runs of the final build, against kills in every earlier step of this round. Each step alone left kills: admission and pressure alone 1 in 3, charging the send queue 2 in 5, the limit of large bodies about every second run. Only all of them together held. 21 clean runs show the kill is rare, not that it cannot happen, so this is not the proof MVP-19 asks for. That takes the independent re-measurement.
- **Open for the initiator.** The defaults. Whether to bound connections: a listener wrapper before TLS could cap them per memory, and would also bound idle keep-alive connections (about 40 KiB each, no limit today). `max_large_in_flight` against slow uploads until the minimum rate is enforced. Whether `client_gone` should leave `blocked` in the request counters. Whether WebSockets should count apart.

## D46 Open connections, what counts as held memory, GOMEMLIMIT, hot reload of local rules (DRAFT / ENTWURF, for the initiator; contracts v0.5)

Trigger: the fourth independent measurement before the first live test. Its attack parameters stay on its own branch, so this entry names causes and limits, not recipes. Backwards compatible for everything served: v0.5 stays unreleased, the new keys are optional, the generator appends and no earlier vector changes. Rules in [body-limits.md](body-limits.md) sections 2a, 2b, 2c and 4.

- **Open connections, new (section 2c).** The measurement ended a 2 GiB container from one address in every run, with almost nothing running: D45 counts requests, an open connection holds memory without one. Stock Caddy dies the same way, so this is a limit the ingress lacked, not a defect of the gate. `waf.connections.max_per_client` 2048, `max_per_network` 8192, factor 4 for `cgnat` and `mobile`, and for the gateway half of the memory at 64 KiB each, so 16384 at 2 GiB (E6 applies). Twice the limits of D45: on HTTP/1.1 a running request holds a connection, and browsers keep others open beside it. An office of 200 browsers on HTTP/1.1 with 200 WebSockets is 1400 connections.
- **In the listener, before TLS.** A listener wrapper of its own in front of Caddy's TLS placeholder, added to the adapted JSON, so the operator's Caddyfile stays as stock Caddy reads it and the way back to stock Caddy is unchanged. It sits on every server, also on the redirects of automatic HTTPS: Caddy creates that server without wrappers, so PrepareIngress writes it out and Caddy puts its redirects there. A refusal costs an accept and a close, no handshake, no goroutine, about 350 ns of decision. It gets no answer because there is no TLS yet: a visitor sees a connection error, not the waiting page. No incident, no event, a gauge and two counters.
- **The oldest idle connection gives way.** Taken from the agent listener of MVP-11 (`TestListenerEvictsWaitingAtCap`), with three changes. It acts at all three scopes, not only at the top: without that a client behind one address locks itself out with its own keep-alive connections, and a flood from many networks that sends nothing keeps visitors off a full gateway. The list is intrusive, so a full gateway costs no scan of 16384 connections per accept. The minimum idle time is 5 s, not 500 ms: under a TLS flood a handshake can take longer than that, and it bounds a client at its limit to about 400 handshakes per second. Busy means a running request or a hijacked connection (WebSocket), reported by the server's `ConnState`, which sits on every server and so also covers sites without schild. The age counts from the opening or the end of the last request. Bytes keep no place: the first draft counted any byte moved in those 5 s, and the fifth measurement held 16384 connections from eight addresses with an HTTP/2 PING every 3 s, or one header byte on port 80, so new visitors got through at 12 to 24 %, at 60 to 64 % on port 80. Holding a place now takes real requests, which the gate counts and limits.
- **The peer is not always the client.** The listener has no headers. A peer in `ingress.trusted_proxies`, and every peer of a server with `proxy_protocol`, counts for the gateway alone. **The cost:** behind a load balancer one client can hold connections up to the gateway limit; there the balancer's own limits and D45 have to do. The wrapper stands before `proxy_protocol` on purpose: reading that header in the accept loop would let any silent client stall every other. A proxy missing from the list counts as one client and meets 2048; the log says so.
- **The limit keeps the container alive, not every request.** With the gateway full of idle connections a new visitor pushes out the oldest one. A client whose idle connection goes in the moment it sends a request gets a reset, and browsers repeat it. When all of them are busy, new connections fail. The same holds while the connections are younger than 5 s: filling 16384 places that way takes about 3300 new connections per second, so a limit in the firewall has to carry that case.
- **What a connection costs, measured again.** 46 KiB of the measurement holds with the collector at its limit. In the builder's runs with room in the heap a full gateway of HTTP/2 connections stood at about 1.4 GiB, so about 80 KiB each, HTTP/1.1 at about 50 KiB. So 64 KiB is no bound on what a connection costs: at 2 GiB a gateway full of idle HTTP/2 connections stands at the edge of level 1 of the brake, at 70 %. A lower limit would keep room for bodies and lock out visitors sooner, the initiator decides.
- **Held memory counts the slab (finding 3).** Now `anon + sock + slab + kernel_stack + pagetables + shmem + file_dirty + file_writeback`. Why, on the 291 runs of the measurement, one sample per second, last peak before each kill, 51 kills of all images: the count of D45 stood at a median of 91 % at the kill, this one at 99 %. Of the 24 kills of the D45 image 2 came without ever crossing 85 %, with the slab none; the median warning went from 6 to 16 s. Why all of the slab: in the builder's runs with every field at 160 ms, 41 to 102 MiB of `slab_reclaimable` still stood at the kill of connections, a third of the slab. These are inodes and dentries of open sockets, the kernel cannot drop them while the socket lives. `slab_unreclaimable` alone reached 94 to 97 %, with all of it 97 to 100 %. Why not page cache: surviving runs reach 100 % of `memory.current` in one of ten (p90), with up to 1.4 GiB of cache, so counting it would hold the brake on through any upload. `active_file` does not help: it was under 25 MiB at every kill of these runs. `kernel_stack`, `pagetables` and `shmem` add 3 to 4 MiB here, and they belong to the same class.
- **What stays uncounted.** Kills with a lot of clean cache remain: in one of the 24 runs, on the host network image, `memory.current` stood at the limit with 911 MiB of cache and the count at 64 %. A burst of `sock` is charged without reclaim, and the cache does not go fast enough. The fields here do not tell that case from the many runs that survive with as much cache. `memory.pressure` might; that is not in this round.
- **The thresholds stay at 70 and 85 % (section 2b).** With the slab every kill of the D45 image was warned of at both. 80 % warns of no further kill and holds surviving runs at the level almost twice as long (9.0 against 5.3 % of their samples); 90 % misses one. Level 1 reaches 120 instead of 116 of 226 surviving runs, level 2 reaches 57 instead of 31, because a fuller gateway now shows up. After the connection limit the slab stays under about 70 MiB, 3 % at 2 GiB.
- **`GOMEMLIMIT` no longer switches the brake off (finding 8).** The limit of the cgroup is read beside it, the levels run, and the Go limit follows the kernel down from the operator's value as from the derived one. A value above the container limit is not refused. Without a limit of a cgroup v2, or with an unreadable `memory.stat`, no brake runs: a warning at the start, `schild_memory_pressure` at `-1`, so the gauge no longer looks like calm.
- **Hot reload of local rules (finding 4).** `SIGHUP` and `schild rules reload`, the CLI over the control path, no dashboard action: D32 keeps rules in the operator's files, and this loads what is there. The collision with the WAF lifecycle is small, because hub updates already do this: instances are immutable, `Engine.Swap` is atomic and requests in flight keep their instance (B07). `Manager.ReloadLocal` builds outside the lock like `PrepareHub`, with CRS, network and hub rules, so a set can only go live if a start would take it. A swap of another source meanwhile starts the build again. What depended on the text at start now follows: the ids a hub rule may not take, and the config version of the agent API. A set that does not build changes nothing, also when it takes the id of a running hub rule. A directory that vanished is refused: the glob would read it as empty and take every exception off in silence. An empty directory is an answer of the operator and goes through. **Limits:** a truncated file that still compiles goes live, as it would at a start, so the runbook says to rename into place. No event yet, only the log and `schild_local_rules_reloads_total`: a new event type is a contract of its own, open below. `schild.yaml` and the Caddyfile still need a restart.
- **`client_gone` leaves `blocked` (finding 10).** A client that left or stalled counts as `client_gone` in `schild_requests_total` and the hourly summary, and not in the rolling count of blocked requests. Nobody blocked it. This takes back that sentence of D45 and answers its open point, for both, since they are one code. The status 400, `rejected_limit` and `schild_bodies_aborted_total` stay.
- **Text corrected.** "40 requests per second with a backend of 25 s fit" in D45 and section 2a holds only without a body. With a body D44's 64 MiB bind at about 512 requests, after about 13 s. The limit stays as it is.
- **Not changed:** defaults of D44 and D45, `max_per_client` stays a proposal.
- **Option for slow uploads, not built.** The measurement shows 256 slow uploads closing `max_large_in_flight` for up to 6 minutes. The window of D41 already sees them (`schild_bodies_below_min_rate_total`). An option: when the gateway stands at three quarters of the limit, a large body that fell under 1 KiB/s in its last complete window ends with 408 `body_too_slow`, the oldest first. Not above that mark, so a slow line on a quiet gateway goes on. **The cost:** a real upload on a bad line loses its work exactly when the gateway is busy; the numbers need the histogram of week 1.
- **Builder's check, no measurement (arm64, Docker Desktop, shared machine under load, a lab backend, `--memory 2g --cpus 2`, attack shapes of the measurement run from its branch; the builder does not measure its own work).** Connections from one address and from two: no kill in 6 runs, the gateway stopped at 2048 per address, at 17 to 20 % of the memory, visitors at 100 %. Through a trusted proxy, so only the gateway limit met them: no kill in 6 runs, 16384 open, 70 % on HTTP/2, 47 % on HTTP/1.1, visitors at 99 to 100 %. Connections plus bodies: 0 of 5 (90 %, GET 95 to 100, forms 49 to 56 %). Bodies from many networks: 0 of 5, the mix 0 of 3. With `GOMEMLIMIT=1638MiB`: 0 of 8, against 7 of 13 in the measurement, the gauge moved and the Go limit fell to 819 MiB. ## D51 What an incident needs stays as long as the incident (2026-10-31, initiator; contracts v0.5)

An incident lives 14 days, its context 48 h and the full address 7 days. Whoever looks at a case in the second week, or has to answer for it later, finds the number and not what happened. The initiator (2026-10-31): it must stay possible to trace a case later, also for legal reasons. ## D52 Livewire snapshots skip CRS, text fields get an exception per domain (2026-11-01, initiator; contracts v0.5)

In autoblock schild answered 403 on normal math text in a Livewire tool, because a single CRS rule at PL1 scores 5 and the threshold is 5. A file download costs almost nothing, but a Livewire action sends all public state in a signed snapshot, and CRS read it as one long field. Measured with the real gateway on 2 cores: text with `$f(x)$`, `x_{1,2}`, `\sin(x)` or `5$ (netto)` got 403, 100 KB of text took 1.1 s in every mode. Accepted risk: with a leaked `APP_KEY` a forged snapshot passes the WAF unseen. Rotating that key is the remedy, a WAF rule was never the protection there.

## D53 HA group: shared control state in Valkey, nothing in the request path (DRAFT / ENTWURF, direction decided by the initiator 2026-11-01; MVP-27, not built)

**Amended by D105 (draft, 2026-11-21): the group shares its state from node to node, Valkey is gone.** What stands is marked there.

One website can run on several servers. The initiator asked for a shared store for sessions and the like. Decided: yes for the control state, no for the data of every request.

- **Shared:** blocks, certificates, allowlist, IP exceptions, suspensions set by a person, users, sessions, agent tokens. **Local:** events, incidents, metrics, rate limit counters, learning, `local_brake`. A limit therefore acts per node, up to n times over n nodes. Why: a network call per request would add a failure point and cost, and the volume of events belongs to the copy of MVP-20.
- **No request waits for Valkey.** Every node keeps a full local copy and decides from memory. A lost store costs the sync, never traffic, and a restart during the outage still serves certificates. An empty or restored store deletes nothing on a node.
- **Valkey is a transport, not a trust root.** Values are sealed with a group key outside Valkey. Valkey sees no address, password hash or private key, and a write without the key can neither allowlist an address nor lift a block. Accepted: a holder of the Valkey password can delete or replay, the nodes then run on their copy.
- **Configuration stays code (D32).** Mode, limits, rules and the hub state stay in `schild.yaml` and `rules.d`. In a group the dashboard shows them read-only, because its kv overlay would drift between nodes. IP exceptions are not configuration: a release in the dashboard sets them, with an expiry, so they are shared.
- **Blocks in a group (amends D32, G1 stands).** D32 lets a person pick the gateways of a block. A group shares every block automatically, also from autoblock, because a balancer makes its nodes one ingress. A group is one operator, nothing leaves it. Every receiving node decides again with its own allowlist and exemptions, and only the deciding node writes the incident.
- **Privacy.** An erasure reaches every node of the group and stays erased after a node returns. Nothing in Valkey outlives the same data on a node.
- **Network mode stays out in v1.** Nodes of one operator must not count as independent operators.

Trigger: a rule exception in `rules.d` is manual work on the server, and the initiator's verdict is that nobody will do it. Setting it in natural language through an agent is the point. The rendering has Go tests only, no vectors, so Python does not check it.

## D57 Crawler control: operators block crawlers per website (2026-11-02, initiator "GO"; MVP-29)

Operators decide per website which crawlers may fetch it, like Cloudflare's AI Crawl Control, without pay-per-crawl. MVP-22 (D35, question 5) left "blocking or charging AI crawlers, robots.txt enforcement" to a separate decision; this is it, for blocking only. Charging and robots.txt enforcement stay out. Spec [../specs/MVP-29-crawler-control.yaml](../tests/specs/MVP-29-crawler-control.yaml).

- **Policy per website.** `categories` (the eleven catalogue categories) and `bots` (catalogue ids), each `allow` or `block`, and `impersonators` `allow` or `block`. Absent keys allow: a website without a policy, or with one that only allows, behaves exactly as before. Unknown categories and bot ids are refused (`contracts/crawler-policy.schema.json`, `contract/crawlers`); `likely_automated` and `likely_browser` cannot be named.
- **Precedence.** `impersonators: block` first: a request that names a crawler whose operator publishes ranges, from an address outside fresh ranges (`mismatch`), is blocked, also when that crawler is allowed (an allow is for the real one). Then a rule for the bot (it overrides its category), then the category. Stale ranges (`unknown_stale`) and crawlers without ranges (`claimed`) are never impersonators; with `bots.verify.ranges: false` nothing is.
- **A block needs no verification.** A request whose User-Agent names a blocked crawler is blocked, verified or not: it identified itself. Only crawlers that name themselves are covered; the dashboard says so.
- **Preset `block_ai_training`.** Blocks `ai_training`, allows every other category, drops the bot rules, keeps `impersonators`. One action in the dashboard and the agent API.
- **Mode.** As every protection: `observe` records `would_block` (reason `gateway_observe`), `review` and `autoblock` answer 403 with a short plain body. An allowlisted address is never blocked by a crawler rule, it is recorded as `would_block` (reason `allowlist`).
- **In the gate** right after the access lock (D56), before behaviour, admission and the WAF: a blocked crawler costs no evaluation. The policy of each website is a table of one byte per catalogue bot plus the impersonator switch, built when the policy changes and swapped atomically; the request path reads a pointer, a map entry and a byte, with no lock and no allocation. The bot id comes from the UA cache the monitor already keeps.
- **Outcome `blocked_crawler`.** Appended to `RequestOutcome` (request ring, `website-visitor` and `request-recheck` enums), optional `TrafficCounters.blocked_crawler` as part of `stopped`, metric `traffic.blocked_crawler`. A crawler `would_block` counts in `would_block`, not in `detections`, pins no context and is no alert of the request ring (rule and page alerts, false-positive hints, visitor patterns). The request ring marks a record the crawler policy alone decided, so the bot overview shows `blocked` and `would_block` per bot; a request the WAF would also have blocked counts as the WAF's.
- **No flood.** No incident per blocked request, its event is sampled like a rate limit. Counts per website, bot and outcome in memory since the start (agent API) and `schild_crawler_requests_total{bot,outcome}`. Prometheus: `schild_http_requests_total{class="blocked_crawler"}`; `schild_requests_total` keeps the decision outcomes, a blocked crawler counts there as `blocked`.

## D60 Connections and waiting requests share the memory, 100 HTTP/2 streams per connection (2026-11-02, initiator; contracts v0.5)

Trigger: round 6 of the measurement before the live test (its attack parameters stay on its branch). Plain GETs over HTTP/2 from a few addresses, and an HTTP/2 client that reads nothing, ended a 2 GiB container in every run, in both images, in `autoblock` too. The likely cause: D46 sized the connections to half of the memory and D45 the waiting requests to the other half, each on its own, and HTTP/2 lets one connection keep sending requests without waiting for answers. With `max_open: 8192` the gateway lived in one run of each. The initiator chose to share the budget and to bound the streams (2026-11-02, "Budget teilen + h2-Streams").

## D73 Rule repositories: OWASP CRS, CrowdSec Hub and own rules behind one interface (2026-11-06, initiator; contracts v0.6)

Trigger: the initiator (2026-11-06): "ich hätte gerne einen sauberen RuleRepository und Rule Domain aufbau. Also Crowdsec, OWASP und später schild network sollen repositories sein, die man sauber verwalten und später evtl. weitere repositories einklinken kann. Alles sollen das selbe Interface implementieren". Asked about dropping mode `review`: "wieso nicht die globalen drei modi lassen? Fand ich eigentlich schön nutzerfreundlich". Before the alpha: "voller umbau". Replaces the per-source parts of D39 and its amendment, D46, D48, D54 and D55 where they differ; D32 stays for everything not named here.

- **Repository.** A rule repository is a source of WAF rules with an id, a state, a set of rules and an origin. The first version has three, fixed and always present: `crs` (OWASP CRS, built into the binary), `crowdsec` (CrowdSec Hub virtual patches: image snapshot plus updates from the hub, D39/D43) and `local` (the operator's files in `rules.d`). The same ids are used in `schild.yaml`, both APIs, events and the dashboard. Further repositories (the Schild network, signed CRS packages of our own pipeline) come only through `schild.yaml` and only with their own decision.
- **One state per repository:** `off` (no rules, nothing fetched), `detect` (rules match and are logged, never block), `block`. Defaults: `crs` and `local` `block`, `crowdsec` `detect`. A value set in the dashboard or through the agent API goes to the settings overlay and wins over `schild.yaml` until `reset_state` (D39 pattern for every repository; `state_source` default/config/dashboard/agent, `state_set_by`). `off` against the others rebuilds the WAF, `detect` against `block` changes only the decision. No password on the switch (D39 amendment).
- **The three modes stay** and mean one thing each for every repository: `observe` nothing blocks (`would_block`); `review` ("Freigeben") rules a repository receives from outside while the gateway runs act only after a person approves them, what ships with the release and what the operator writes counts as approved; `autoblock` such rules act on their own after `settling_s`. In the first version only `crowdsec` receives rules at runtime; its image snapshot is release. This replaces "in `review` the hub only detects" of the D39 amendment.
- **One rule vocabulary.** A rule is `{repository, id}`; `id` is the SecRule id as a string (`crowdsec`: the base id of D39, the hub name is `name`). `origin`: `release`, `update` or `operator`. `status`: `active`, `pending` (an update waits for approval, mode `review`), `settling` (an update waits for `settling_s`, mode `autoblock`), `disabled` (`disabled_by` config, dashboard or agent), `rejected` (a person refused this version). `effect`: `off`, `detect`, `would_block`, `block`, with `limited_by` (`gateway_observe`, `repository_detect`, `pending`, `settling`) when the effect is lower than the repository state. One pure function in `contract/rules` computes status and effect from mode, repository state, origin, approval, disabled and settling; Go and Python agree on its vectors (`rule-effect`). The CRS still blocks by anomaly score; a CRS rule's effect is that of its repository.
- **Approval.** Approve and reject are per rule and version. A changed rule (new version) waits again; a rejected version never runs, the next version is pending again. Approving acts at once, without settling. Records in `schild.db`, one table for all repositories (disabled, approved, rejected, with who, when and note).
- **Disabling one rule works in every repository:** in `schild.yaml` (`disabled_rules`: ids for `crs` and `local`, hub names for `crowdsec`) and in the dashboard or agent API. A rule disabled in the file cannot be enabled elsewhere (409 `config_limit`). CRS and local rules are removed with `SecRuleRemoveById` at build, which rebuilds the WAF.
- **One composer.** Every repository hands its rules to one composer, which builds and swaps the WAF and owns the checks: id range per repository (`crs` 900000..999999 and the built-in 200000..200099, `crowdsec` 60000000..99999999, exceptions 1900000..1999999, network 7700000..7799999 reserved, `local` everything else), and for rules from outside the bounds, SecLang subset, cost and compile checks of D39/D43, which move there unchanged. Signatures and a monotonic version are required for every later repository that fetches rules (CRS packages, network); the first version has none that needs them.
- **API, the same in the dashboard (`/api/v0`, session and CSRF) and the agent API (`/agent/v0`, bearer token):** `GET /rule-repositories`, `GET|PATCH /rule-repositories/{repository}` (state or `reset_state`), `POST /rule-repositories/{repository}/sync` (`crowdsec` checks now, `local` reloads `rules.d`, `crs` 409), `POST /rule-repositories/{repository}/reset` (`crowdsec` back to the image snapshot, others 409), `GET /rules` (every rule of every repository, filters `repository`, `status`), `GET|PATCH /rules/{repository}/{rule}` (`disabled`), `POST /rules/{repository}/{rule}/approve|reject`. Repository-specific fields sit in one object per repository (`crs`, `crowdsec`, `local`) next to the shared ones. Gone: `/rules/crowdsec-hub`, `/rules/crowdsec-hub/reset`, `/rules/{rule_id}/suspend|resume`, agent `/crowdsec-hub`, the CRS-only `listAgentRules` shape. `POST /rules/test` stays.
- **Scopes.** `crowdsec:write` becomes `rules:write` (repository state, sync, reset, disabling a rule). `rules:approve` is its own scope for approve and reject, so an agent that tunes rules does not also approve updates. `exceptions:write` stays. Tokens with a write scope need `--label`.
- **Exceptions** name a repository and its rule ids: `crs` and `crowdsec` (all SecRules of the base id); `local` is refused (`not_supported`), its rules are the operator's own file. Shape, cap and history as in D54.
- **Config.** One block `rules` replaces `waf.crs`, `crowdsec_hub` and `SCHILD_LOCAL_RULES`: `rules.crs` (`state`, `paranoia_level`, `inbound_anomaly_threshold`, `livewire_exception`, `disabled_rules`), `rules.crowdsec` (`state`, `auto_update`, `interval_s`, `pin`, `settling_s`, `disabled_rules`), `rules.local` (`state`, `dir` default `/etc/schild/rules.d`, `disabled_rules`). `waf` keeps the engine limits. Old keys are refused, no aliases: nothing is installed yet.
- **Events.** `matchedRule` names `repository` (`crs`, `crowdsec`, `local`) instead of `source`, `crowdsec` instead of `hub`. Decision sources `crs`, `local`, `crowdsec:<id>`, `limit`. Rule events `schild.rule.repository_switched.v1`, `schild.rule.repository_updated.v1` (update, refusal, reset, reload), `schild.rule.disabled.v1`, `schild.rule.enabled.v1`, `schild.rule.approved.v1`, `schild.rule.rejected.v1`; `exception_set` and `exception_removed` stay. Annotation `rule_repository_changed`.
- **Version:** contracts v0.6, unreleased, not backwards compatible with v0.5 for rules, config and events. Nothing is installed outside the test lab.
- **Open.** Per-repository approval policy (only once a second repository receives rules at runtime). The dashboard's inbox of D62 lists pending rules once it is built.

## D75 Store migrations: forward only, with a backup, only at the gateway's start (2026-11-10, lead for the release 0.1.0-alpha.1; contracts v0.6)

Trigger: the first public release. From it on an update must not ask anyone to delete `schild.db`. Replaces "One store schema" of D74 for every release from 0.1.0-alpha.1 on; D74 stays for builds before it.

- **Baseline.** The schema of 0.1.0-alpha.1 is schema version 1 (`PRAGMA user_version`). A new file gets the baseline and then every migration, so there is one path to the newest schema. The table `schema_migrations` (version, name, time) is the history.
- **Migrations** are numbered without gaps, forward only, plain SQL, and never edited after a release. There is no downgrade.
- **Only `schild run` migrates** (`store.OpenMigrate`). Every other command (`schild allow`, `token`, `status`, the stopped-gateway path of `dashboard reset-password`) opens with `store.Open`, which refuses an older database with `ErrNeedsUpgrade` and asks for a restart. A command never alters the database of a gateway that runs an older binary.
- **Backup first.** Before the upgrade the gateway writes a consistent copy with `VACUUM INTO` to `<db>.backup-v<N>` (`N` = the old version, mode 0600). Without the copy there is no upgrade and the gateway does not start; the error names the free space needed (about the size of the database). One generation is kept; earlier copies go after a successful upgrade.
- **One transaction.** All pending migrations and the new version commit together or not at all. After a failure the database is unchanged and the error says so.
- **Refused, nothing written:** a database of a build before the baseline (D74 message: move the file away) and a database of a newer schild (start the newer version, or put the backup back).
- **Not covered:** `metrics.db` and the request ring keep their rule (another layout starts over, D36, D74); they hold no settings.
- **Open.** A migration that needs Go code instead of SQL gets its own decision. The disk budget (D38) does not count the backup copy.

## D76 Dashboard access: the session cookie over plain HTTP, and a Host check (2026-11-10, lead for the release 0.1.0-alpha.1; contracts v0.6)

Two findings before the release. First: the session cookie was `Secure` for every host but `localhost` and `127.0.0.1`, so a login over plain HTTP under another address (`http://10.0.0.5:8788` in a VPN, a name in `/etc/hosts`) answered 200 and the browser dropped the cookie. Second: the dashboard answered under any `Host`, so a page on the internet could reach a loopback dashboard through DNS rebinding (the Origin check covers changes, not reads by a rebound same-origin page).

- **Cookie.** `Secure` when the request came over TLS or a proxy says so (`X-Forwarded-Proto: https`). Not `Secure` on loopback (`localhost`, `127.0.0.0/8`, `::1`). Otherwise `Secure` unless the browser itself states it loaded the dashboard over plain HTTP (`Origin` equals `http://` + `Host`); a login without that proof keeps `Secure`. `HttpOnly` and `SameSite=Strict` as before. Plain HTTP beyond loopback stays the operator's choice (tunnel or VPN, D40); the dashboard does not refuse it.
- **Host check.** Every request but `/healthz` and `/readyz` needs a `Host` that is `localhost`, an IP address literal (an address cannot be rebound; this keeps Docker port mappings and VPN addresses working), the host of `listen.dashboard`, or a name in the new key `dashboard.allowed_hosts`. Anything else: 403 as plain text that names the key and shows the YAML line, and one warning in the log per name and minute.
- **Config (`config-schild`).** `dashboard.allowed_hosts`: at most 32 unique host names, lower or upper case, no port, no scheme, no wildcard. Default empty. Vectors valid 072, 073, invalid 175 to 179; no earlier vector changes.
- **Changes behaviour:** a dashboard opened under a DNS name (own reverse proxy, VPN name) needs the key from this version on.

## D79 The Caddy swap is the default way in: `schild init -caddyfile`, a copy of the certificate storage (2026-11-10, lead for the release 0.1.0-alpha.1)

- **Default audience.** An admin who runs Caddy and switches to schild, the Caddy distribution with the WAF module built in. Docs, website and READMEs show this setup first ("Du nutzt Caddy: Schild als Caddy-Distribution"; the wording never says that schild replaces Caddy); the proxy behind nginx, Apache or a load balancer is the second scenario. Both stay supported; the config contract does not change (ingress mode, D31).
- **`schild init -caddyfile FILE [-caddy-storage DIR] [-config FILE] [-node-name NAME] [-force]`** writes a commented starter `schild.yaml` in observe mode with `ingress.caddyfile: FILE` and `ingress.storage: /var/lib/schild/caddy`. It refuses a missing or broken Caddyfile before anything is written. `-caddyfile` with `-upstream`, and `-caddy-storage` without `-caddyfile`, are usage errors (exit 2). Rules for the file (no overwrite without `-force`, no symlink, mode 0644) as in D78.
- **The Caddyfile is never rewritten.** init and `schild ingress validate` list every site, name the sites that still need `import schild` and print the snippet `(schild) { schild }` when the file does not define it. The admin adds the lines. A site that reaches a backend without `schild` stays a refusal at start (D31).
- **Certificates: a copy, not a shared directory.** The admin copies Caddy's storage once into `/var/lib/schild/caddy` (systemd: three commands that init prints with the detected source: `-caddy-storage`, else the Caddyfile's `storage file_system`, else `/var/lib/caddy/.local/share/caddy`, `/data/caddy`, `/root/.local/share/caddy`; Docker: a helper container of the caddy image, in Compose the one-shot service `certificates`). Reasons: Caddy's storage is never written, so the way back does not depend on anything schild did; the unit needs no path outside `/var/lib/schild`; no file of the user `caddy` changes owner or mode. Trade-offs: private keys exist twice on the host, and a certificate schild renews is not in Caddy's storage (after the way back Caddy uses and renews its own). Not chosen: a shared group or ACL (Caddy writes 0600 files and 0700 directories, so it breaks at the next renewal), chown of Caddy's storage (breaks Caddy), running schild as the user `caddy` through a drop-in (shares everything in place, but a newer certmagic then writes into Caddy's storage and the unit depends on a user of another package).
- **Ports 80 and 443 without root.** systemd: user `schild`, `CAP_NET_BIND_SERVICE` as the only capability (ambient and bounding set), the rest of the hardening unchanged. Container: uid 65532, `--cap-drop ALL`, read-only root file system, `no-new-privileges`; Docker sets `net.ipv4.ip_unprivileged_port_start=0` in the container's network namespace, so no capability is added. This does not hold with `--network host`, which the quickstart does not use. The dashboard is published on the host's `127.0.0.1` only.
- **Check before the swap.** `schild ingress validate` run as the user schild will run as, while Caddy still serves, adapts the Caddyfile, and then checks what would break after the swap; each is a refusal with the reason, the consequence and the command that fixes it (`result: REFUSE (…); consequence`, exit 1): (0) this user cannot write the data directory or a file directly in it (`gateway.lock`, the databases), or cannot create it; schild would not start. The `StateDirectory` of a loaded `schild.service` is exempt, systemd hands it over at start; (1) `ingress.storage` exists but this user cannot read it (schild would not start or the sites would fail) or cannot write it (schild starts, but could not renew or store certificates), down to every directory and file (certificates, keys, local CA, ACME account); a storage root that is a symbolic link is followed and its target walked, a link to nowhere is refused (without a `chown`, which would not help), links inside the storage are skipped. Fixed by the printed `chown -R`; without systemd (a container) the command is numeric, without sudo, and names the data directory when the storage lies inside it, as the documented copy command does; (2) Caddy provisioning with a throwaway storage fails; (3) this user cannot write a log file of the Caddyfile (the advice creates a missing directory with `mkdir -p` and uses the container wording without systemd); (4) under systemd, a log file is outside what the loaded `schild.service` with `ProtectSystem=strict` may write (`ReadWritePaths`, `StateDirectory`, `LogsDirectory`, asked with `systemctl show`), fixed by the printed drop-in. It warns, and then ends with `result: PASS with warnings`, about a unix socket this user cannot connect to, about a log file outside `/var/log/caddy` and the data directory when systemd runs but the unit cannot be read (the service user needs the system bus for `systemctl show`; root does not, so the warning names `sudo schild ingress validate`) or is not installed (`LoadState=not-found`; the warning says so instead of pointing to root), and when it ran as root with files to check (root may do everything, so the hint to run it as the service user is printed only then). Without systemd (no `/run/systemd/system`, a container) there is no unit sandbox to check. The unit allows writing to `/var/log/caddy` when it exists (`ReadWritePaths=-/var/log/caddy`); other log directories need a drop-in.
- **One report, one stream.** The report of `schild ingress validate` goes to stdout in order, with exactly one result line, the last (`result: PASS (Caddyfile)` only with `-adapt-only`); a refusal is not repeated on stderr. During provisioning Caddy's default log shows errors only, so its info lines do not interleave; a provisioning error is printed as the reason of the refusal.
- **`-adapt-only` is the Caddyfile only.** No look at the data directory or the certificate storage (no certificate count), no provisioning, no file access; it prints what it did not check. The Docker and Compose steps use it for the first look at the Caddyfile and run the full check after the copy.
- **The full check runs where schild runs.** Provisioning needs a temporary directory; when the system's temp directory is not writable (container with `--read-only`), the check uses the data directory, which it has just found writable, and removes it again. The documented containers stay read-only without a tmpfs.
- **Compose copies at the full check.** `docker compose run --rm --no-deps schild ingress validate -adapt-only` does not start the one-shot service `certificates`; `docker compose run --rm schild ingress validate` does (copy, then the full check as uid 65532), right before the swap. The copy is never overwritten once it exists, because schild renews in it.
- **The way back.** Stock Caddy refuses the directive `schild`, so the documented way back is: `#` in front of the line `schild` inside the snippet (the `import schild` lines stay valid with an empty snippet), then stop schild and start Caddy. For the same reason the docs say not to reload or restart Caddy between the edit and the swap.
- **Said plainly.** In this setup schild carries all traffic from the swap on. Observe mode blocks nothing, but there is no fail-open: while schild is down the sites are down. Website, docs and the output of init say so.
- **HTTP/3.** The Docker steps publish 443/tcp only: schild still announces HTTP/3 in `alt-svc`, the UDP port is closed, browsers stay on HTTP/2. With systemd HTTP/3 stays as the Caddyfile says and init prints a note (D41: HTTP/3 ignores the `read_body` timeout).
- **Packaging.** `gateway/deploy/quickstart/caddy/` (`compose.yaml`, `schild.yaml`) next to the unchanged proxy quickstart; the release workflow checks the version in both compose files. One systemd unit for both setups. `TestCaddyQuickstart` keeps the quickstart config in line with what init writes.
- **Measured for the check (builder's own run, not an evaluation):** in the Debian 12 systemd container a copy still owned by `caddy` and a log directory outside the unit's paths were each refused by the check, and schild did fail to start in both states; with the `chown` and the drop-in the check passed and schild started. Without `dbus` in that container the service user got the warning and root the refusal. In the read-only Docker container the full check passed after the documented copy and refused a copy owned by root.
- **Measured (builder's own run, not an evaluation):** Docker (caddy:2.11.7 to schild, arm64) and systemd (Debian 12 with Caddy 2.6.2 from apt, in a container): the sites answered with the same certificates before and after the swap and after the way back, and nothing was issued. Certificates were `tls internal`; a storage with ACME certificates, amd64 and dnf-based systems were not run.

## D80 Operator rules cannot switch the rule engine or the request body off (2026-11-12, lead for the release 0.1.0-alpha.1)

- **Finding (security review).** The gate forwards the request body Coraza has buffered. With the rule engine or the body access off, for every request (`SecRuleEngine Off`, `SecRequestBodyAccess Off`) or for one (`ctl:ruleEngine=Off`, `ctl:requestBodyAccess=Off`), Coraza buffers nothing and reports no error: the backend got an empty body with status 200 on the way in. Reproduced with all four; a webhook left out of the WAF this way lost its payload silently.
- **Refused at build.** `waf.Build` refuses operator SecLang (`rules.d` and exceptions) that contains `SecRuleEngine`, `SecRequestBodyAccess`, `SecRequestBodyLimit`, `SecRequestBodyNoFilesLimit`, `SecRequestBodyInMemoryLimit`, `SecRequestBodyLimitAction` or the actions `ctl:ruleEngine`, `ctl:requestBodyAccess`, `ctl:requestBodyLimit`, in any case, also in a chained line or after a line continuation. The message names the directive and what to use instead. At a start the gateway does not come up; at a sync the running rules stay (as for every set that does not build, D73).
- **Why refuse and not support.** The mode (observe, review, autoblock) and the switch of each repository are schild's own settings, and so are the body limits (`limits` in `schild.yaml`); a second place that overrides them per request would make the dashboard state wrong. Leaving a path out of the CRS stays possible with `ctl:ruleRemoveByTag=OWASP_CRS` or `ctl:ruleRemoveById`; the hard limits and the operator's other rules then still apply and the body is passed on complete (test `TestLeavingAPathOutKeepsTheBody`).
- **`Include` is refused with them.** With the CRS off, an operator file could include any file of the host, and that file passed this check and the check of the id ranges unseen (reproduced: `Include` of a file with `SecRuleEngine Off` built). The rules directory is the one place for operator rules, read in name order.
- **The net behind it.** `waf.ReadBodyInfo` answers `ErrBodyBusy` (503) for a transaction whose engine or body access is off, whatever led there. An empty body never reaches the backend as if it were the request. Tests: through the gate (`TestNoRequestWithAnEmptyBodyReachesTheBackend`), at a start (`TestStartRefusesRulesThatTakeTheBodyAway`) and at a sync (`TestReloadRefusesABadFile`).
- **No contract change.** The config contract and the remote rule subset (`contracts/seclang-subset.md`, which already rejects all of these) do not change.

## D81 The server check judges the firewall for IPv6 too (2026-11-12, lead for the release 0.1.0-alpha.1)

- **Finding (security review).** `firewall.active` and `firewall.default_incoming` read `nft list ruleset` without regard to the address family, else `iptables-save`, which lists IPv4 only. A host with a default deny for IPv4 and no rules for IPv6 was reported as ok although every listening service was reachable over IPv6.
- **Per family.** The nft ruleset is read once per family: tables of the family `ip` (or `ip6`) plus the `inet` tables, which filter both. With iptables the check also runs `ip6tables-save` (read only, fixed argv, in the command list of `schild check -privileges`).
- **IPv6 counts when the host is reachable over it.** The check reads `/proc/net/if_inet6`: an address in 2000::/3 with global scope. Loopback, link-local and unique local addresses do not count; without such an address the result is the IPv4 result as before.
- **Results, same check ids.** IPv4 filtered, IPv6 not: `firewall.active` is a finding (high, "Firewall filtert IPv6 nicht"). IPv4 default deny, IPv6 default accept: `firewall.default_incoming` is a finding (medium). IPv6 rules not readable (no `ip6tables-save`): both are `unreadable`. No fix command: the right one depends on how the IPv4 rules are kept. When IPv4 itself is a finding, or the state comes from the ufw or firewalld configuration because the ruleset is not readable, nothing changes; firewalld and ufw with `IPV6=yes` manage both families.

## D109 A block of the group is one record under its incident number, and a lift is a record of its own (2026-11-26, initiator)

- **Finding (three independent reviews of one fix).** In 0.1.0-alpha.6 a block and its lift share one record per client address. As soon as one client has two blocks (two nodes block at the same moment, a full table drops a block and the client is blocked anew, a release is followed by a new block), a node has to guess whether its lift may replace the record it finds. Three rules for that guess were built; each lost a lift or ended another block in some order of arrival. The audit log (MVP-36), the integration API (MVP-35: `POST /blocks/{incident}/release`) and the dashboard all name a block by its incident already, and the website scope (MVP-34) needs several blocks of one client at once.
- **The incident number is the identity of a block in the group.** Class `incident_blocks`: one record per block, id the incident number, never a tombstone, with a `scope` (`gateway`, the only one for now). A node that draws a number it knows draws another. Two blocks of one client are two records and never touch each other.
- **A lift is a record of class `lifts`**, id the incident number, without an address. It ends its block whatever arrives first and whatever the clocks say, and a node that holds it drops the block record. Chosen over a tombstone decided by the clock: a block of a node whose clock is up to 60 s ahead would beat a later lift. No node writes a record for another node's decision any more.
- **A person releases the client, an agent the incident.** "Freigeben" of an incident in the dashboard lifts every block the node holds for that client, one lift per incident, as `fail2ban unban` and `cscli decisions delete --ip` do for an address; the 24 h exception of D87 is for the client already. The agent API lifts the one incident it names.
- **A lift is noted in `schild.db` with the change that made it** and written to the group until that succeeds, also after a restart. The audit log will write its entry in the same transaction (MVP-36).
- **Erasure.** A node that holds the erasure of an address stores no block of that client from before the erasure, so a node that was away does not bring it back. Within the 60 s two clocks may differ the erasure wins.
- **An unknown class is kept unread, as an unknown version is** (check 3a), and a node reads again at its start what it kept. 0.1.0-alpha.6 refused an unknown class for good, which is why D109 is a cut at all; the next class or record version (audit log, portal keys, the website scope of MVP-34) needs none. Rejected: taking website blocks now and not enforcing them. A node would hold blocks as its state that it does not apply, without saying so.
- **Hard cut (initiator: "harter schnitt, ist ja noch alpha").** A build before D109 refuses the new classes, so old and new nodes share no blocks while both run. All nodes of a group are updated together, and the blocks and lifts the group shared before are not carried over. Class `blocks` is gone: a node refuses a record of it for good and deletes at its start the ones it holds. Rejected: switching by the build version of every member; it keeps both models and the moment of the switch in the code.
- **2026-11-27: the migration from 0.1.0-alpha.6 was dropped (maintainer).** The first build of D109 read the records of class `blocks` until they were over and moved a node's own blocks and lifts to the new classes at its first start. That is gone: the project is an alpha and no group is in use, so the code and the contract text of the move were not worth keeping.
- **Rejected: a class of lifts next to blocks by client.** It ends the guessing for the lift and keeps one record per client, which MVP-34 cannot use.
- Contract: [cluster.md](cluster.md) sections 2, 4, 5, 13, 14 and 16; Go `cluster.IncidentBlock`, `cluster.IncidentLift`; vectors `cluster-record` rebuilt on the new classes; `unknown-class` now answers `class`.

## D105 Group without a store: gateways share their state from node to node (DRAFT / ENTWURF, direction given by the initiator 2026-11-21; MVP-27, not built)

- **Finding (initiator).** A group should run as a pair of two and as a fleet of about ten nodes, for example at a hoster. Every event and request has to be reachable across the nodes, a failed node must cost neither requests nor protection, blocks may have to act in front of the gateways, and there should be no database cluster beside them: "mehr in peer to peer richtung denken". Replaces the Valkey store of D53. Spec: [MVP-27](../tests/specs/MVP-27-ha-group.yaml), with the projects looked at (checked 2026-11-21).
- **No store, no majority.** Every gateway keeps the full control state in its SQLite file and pushes changes to every other member over a mesh of TLS streams (as HAProxy peers do). Records merge by a hybrid logical clock with tombstones, so two nodes are enough: Raft with two members stops when one is gone. Stands from D53: no request waits for the group, a lost peer costs the sync and never traffic, a receiving node decides again with its own allowlist, only the deciding node writes the incident, nodes of one operator are never independent operators.
- **Members know each other by key.** An Ed25519 key per node, a member list that is itself replicated, a signature per record, no CA. A member is trusted like the operator; `schild cluster remove` ends that for one node.
- **Set up by configuration (initiator, 2026-11-21: "per config file definieren und überall deployen können, z.B. mit ansible").** `cluster.secret_file`, the same on every node, and `cluster.peers`: a node lets itself in at its start, no command goes from node to node. The secret only admits: it signs the admission of a node key, records stay signed by the node, a removed node stays removed. This takes back "no shared secret" of the first draft for the admission, and for nothing else. Join codes stay as the way by hand.
- **What "seamless" means.** A connection that ended on a failed node is lost: nothing open moves a TLS connection to another machine. Everything a visitor carries holds on the next node: block or pass, the passed browser check, the access lock login, the TLS session, the incident number. A planned stop drains and loses no request. schild moves no address and is no balancer: keepalived with a floating address, the hoster's balancer or HAProxy do that, from the runbook.
- **Limits count for the group (amends D53, where a limit acted per node).** No shared counter in the request path. A node sends its own count for a client that nears a threshold once a second, one slot per node, summed. Bound: what the nodes take in one second.
- **Events and requests stay where they were written, with one copy on another node.** A query goes to every member and is merged; a member that is away is answered from its copy, or the answer names what is missing. Every copy obeys the retention, the size cap and every erasure of its origin. Amends D53 and D32: the view across the nodes of a group no longer needs the central dashboard of MVP-20, which stays for several groups and single gateways.
- **Settings of the dashboard are shared (amends D53, open for the initiator).** D53 made the dashboard read-only in a group. Since D89, D93 and D101 the switches of the sources, the thresholds and the CRS levels are set there, so they travel as records. `schild.yaml`, `rules.d` and the Caddyfile stay files and a deployment (D32); a difference between nodes is a hint.
- **Everything set at runtime is shared (initiator, 2026-11-22).** "Wieso syncen wir nicht jede Einstellung, dass wirklich überall alles gleich ist": the default is turned round. Every key of the gateway's key-value store travels in a group as class `settings`, whatever feature wrote it, cut into entries by the shape of its value; a short list of keys that describe one node stays (`installed_at_v1`, the setup code, the hub download status and stored set, a cache counter), next to the server check of each machine, the log of agent calls, the login bound of the dashboard and the files of the deployment. Tables are shared by a decision each; a test fails for a table nobody decided on. The nodes prove it to each other: a keyed hash of what is in force per class, told every 5 s, shown on the cluster page, named on the overview after 30 s and repaired.
- **Own rules stay files (initiator, 2026-11-21).** `rules.d`, `schild.yaml` and the Caddyfile reach every node through the operator's deployment, as D32 says, and the group only names nodes that differ. Sharing own rules through the group was considered and dropped: it would be a second source of truth next to the operator's repository. What a node downloads (the CrowdSec Hub rules, later the bundles of the relays) is shared through the group, so every node decides with the same rules.
- **Blocks in front of the gateways.** Behind a balancer with the PROXY protocol the packets come from the balancer, so the host firewall of D87 holds nothing on a gateway. The balancer VMs join with the role `edge` and run `schild firewall run --group`: they get the drop list and nothing else. Not built: the hoster's cloud firewall (Hetzner: 500 rules, none on a load balancer), RTBH and Flowspec (not offered to customers).
- **Certificates.** A Caddy storage module on the mesh. The lock is held by the reachable member with the lowest id; in a split a certificate may be ordered twice, which is accepted and counted.
- **Edges and join codes removed (maintainer, 2026-11-23).** A group is set up by `cluster.secret_file` and `cluster.peers` only, 2 to 16 gateways behind a load balancer that passes TCP on (a cloud load balancer or HAProxy in TCP mode); TLS ends on the gateways. Edges are gone: a cloud load balancer has no VM to run them on, and the gateways refuse blocked clients themselves. Join codes are gone: they did the job of the secret file a second way, and only edges needed them. No release held either. The two points above that name them stand as the record of the first draft.
- **Hardening before the first release (maintainer review, 2026-11-23).** With `cluster.enabled` a gateway never runs alone while its readiness says 200: a node that cannot be set up or cannot run stops the start, with the cause and the fix in the error (a removed node still starts and serves with what it holds). Readiness counts only the answer of a member that is in step (or was within 30 days), so two fresh nodes do not call each other in step with nothing; a group new as a whole comes in step when every named peer answered. A node away longer than the 30 days a removed entry is remembered takes the group's shared state anew and hands none of its own over, so a removal is not undone by a copy that outlived its tombstone. A node leaves traffic for its clock only by a strict majority of the gateways in view, so one slightly-off gateway does not disable the rule and two against two takes nobody out. The secret file may be `root:schild` 0640. Rules in [cluster.md](cluster.md) sections 3, 5, 6, 7, 8a, 10 and 14.
- **Open for the initiator:** the six questions at the end of the spec, the first being whether settings are shared or read-only.

## D103 The agent API is on by default, has a switch in the dashboard and is reachable in a container (2026-11-21, initiator)

- **Finding (initiator).** The agent API is an important feature, and setting it up took an edit of `schild.yaml`, a restart and a token. With Docker, the second way to install, it could not be reached from the host at all: the listener took loopback only, which inside a container is the container. Nothing in the dashboard showed that the API exists.
- **Rule for this decision (initiator): as simple as possible for the operator, and safe.** The safe state is the default and takes one step; the safe direction (off) is always one click; what would be unsafe does not start instead of warning.
- **On by default.** `agent_api.enabled` defaults to true (D33 had false). The listener alone opens nothing: every call needs a bearer token, a call without one answers 401, and tokens are still created on the host only (`schild token add`), stored hashed, with an expiry. Setting it up is now one command.
- **One command without required flags.** `schild token add` creates a token that reads only (`agent:read`) and holds 90 days; `--expires` is no longer required (1d to 365d as before). A write scope still needs `--label`.
- **A switch in the dashboard.** `getAgentAPI` and `setAgentAPI` (`GET` and `PUT /agent-api`, session and CSRF, no password as in D74). The value is stored in `schild.db` (kv `agent_api_v1`) and holds until `reset: true` gives the switch back to the file. In force before the answer returns, without a restart: the listener opens or closes, calls in flight end. A listener that does not open answers 409 `conflict` and leaves the switch as it was. `AgentAPIState` carries the value, its source (`config`, `dashboard`), the address, whether the listener is open and why not, and the number of valid tokens and of those with `firewall:sync`. `AgentCallLog.enabled` is the value that holds.
- **The file can lock, the dashboard can always switch off.** `enabled: false` in `schild.yaml` is final: switching on in the dashboard answers 409 `config_limit`, as a rule disabled in the file (D73). With the file on (or silent), the dashboard switches off and on again. This is not the pattern of the repository switches, where the dashboard wins both ways: here a dashboard session must never open what the operator closed on the host.
- **The firewall depends on it (D87).** With the agent API off, `schild firewall run` gets no blocks; the blocks it holds end by their kernel timeout. The dashboard asks before it switches off while a `firewall:sync` token is valid.
- **Reachable in a container.** `agent_api.listen` also takes every interface (`0.0.0.0:<port>`, `[::]:<port>`), for a container whose port is published on the loopback of its host (`127.0.0.1:8789:8789`), as the dashboard listener does. Any other address of a network is still refused by the schema. The quickstart `schild.yaml` and `compose.yaml` files carry both lines. The Host check is unchanged: a call has to name `localhost` or a loopback address and the port of the listener, so the published port keeps its number.
- **Every interface only in a container.** Outside a container schild does not open a listener on `0.0.0.0` or `[::]`: on a host it would offer the API to the network over plain HTTP. The gateway runs, the listener stays closed, the log and the card in the dashboard say why. A container is `/.dockerenv`, `/run/.containerenv` or `KUBERNETES_SERVICE_HOST`; where schild does not see it, `SCHILD_AGENT_API_ANY_INTERFACE=1` opens the listener. Runtime behaviour, no contract vector.
- **Dashboard.** The card "Agent-API" under Einstellungen: the switch (absent while the file has it off), the address, the tokens read only (label, scope, state, expiry, last use), the command that creates a token where there is none, and "Wert aus schild.yaml einsetzen".
- **Risks accepted (initiator).** (1) Every gateway now has a second listener, also where no agent is ever connected; local processes and an application with an SSRF hole on the same host reach it and still need a token. (2) D39 and D42 accepted their risks with "the agent API stays off by default". What holds now: the write scopes stay opt-in per token, tokens come from the host only, and the operator can switch the API off in the dashboard or lock it off in the file. (3) In a container the listener is on every interface of the container: another container in the same Docker network reaches it and still needs a token, as with the dashboard listener; a compose file that publishes the port without `127.0.0.1` opens it to the network.
- **After an update.** An existing gateway listens on `127.0.0.1:8789` after the update unless `schild.yaml` says `enabled: false`. If the port is taken, only this listener does not start: an error in the log, "Nicht offen" in the dashboard, requests are not affected. An existing Docker installation needs the two lines above to reach the API from the host.
- **Open.** No event for the switch yet, only the log line with the dashboard user: a new event type is a contract of its own. Tokens are neither created nor revoked in the dashboard. No hint for tokens that expire soon. No direct access over a VPN address. The switch has unit tests of the builder only; no independent measurement.

## D87 One list of every blocked address, and the blocks in the host's firewall (2026-11-18, initiator)

And the blocks were expected in the firewall ("würde voll Sinn machen, dass man aggressive IPs direkt in der Firewall sperrt"), while a block of schild held in schild only (the block page). The firewall part of MVP-15 (D28, draft) was never built.
- **The list.** Client dashboard API `GET /blocks` (`listBlocks`, `BlockList` of `RunningBlock`): every address block that runs now, from the block table and the kept blocks over 24 h, newest first, at most 500 rows with the total. Per row the client (IPv4 address or IPv6 /64, the key schild blocks), source (`scenario` with the scenario, `agent` with the token id), since, until, duration, ladder level, net class, incident (ends it with `unblockIncident`), kept, and the firewall state. Full IPs, local only, like the hits.
- **The firewall, the first step of MVP-15.** `schild firewall run`, the same image or binary as the gateway, runs as its own process with `CAP_NET_ADMIN` in the gateway's network (a second container with `network: host` or `network_mode: service:schild`, or a systemd service). It keeps the nftables table `inet schild` in step over netlink (`google/nftables`, Apache-2.0; no `nft` binary in the image): sets `blocked4` (IPv4 addresses) and `blocked6` (IPv6 /64 as intervals), each element with its remaining time as the kernel timeout, a constant set `web_ports` (80, 443) and one chain on the prerouting hook (priority -150, before Docker's DNAT) that drops TCP and UDP to those ports from the sets. The table is built afresh at start; a clean stop removes it; `schild firewall status` and `off` are the other commands. The gateway itself gets no right on the firewall.
- **Over the agent API, like a CrowdSec firewall bouncer.** New operation `syncAgentFirewall` (`POST /agent/v0/firewall/sync`), new scope `firewall:sync`, which may call nothing else (no read of events, requests or anything). The body says what the firewall applied (revision, clients held, table, version, its last error); the answer is every block that runs (cut at 10000, the ones ending last left out) with its revision. A long poll: the gateway answers at once when the blocks differ from the applied revision, else after 50 s, so a block or a lift reaches the firewall within a second at about one call a minute in the call log. Why not files in the data directory (a first draft of this decision): rights on files of the container's user, a path unit on the host, and no way for a firewall on another host later; HTTP on the loopback agent API reuses tokens, rate limits and the call log the gateway has. Why not fail2ban (an earlier draft): it knows no ban length per client, cannot lift from a log line, and MVP-15 warns against double blocking with it.
- **As MVP-15 asks.** No `policy drop`; every element expires in the kernel, also when the firewall or the gateway is down; the firewall reconciles what schild blocks with what the table holds, and the dashboard says when they differ (`pending`, `stale`). Own table only: other rules, ufw, firewalld and fail2ban stay as they are.
- **Only the web ports, for now.** schild's blocks come from web requests; SSH and every other port stay open, so no operator locks themself out and no dead man switch is needed for this step. All ports, SSH failures, port scans and Spamhaus DROP stay MVP-15 (D28, draft).
- **Versions.** Gateway and firewall are the same image; the versioned path `/agent/v0` holds them together as the API of CrowdSec does. The token expires after at most 365 days like every agent token; the dashboard then shows the firewall as stale.
- **Freeing an address frees it in the firewall.** Unblocking an incident in the dashboard used to add a 24 h exception for the client and leave the timed block running; the client passed, but the block stayed in the list, and would have stayed in the firewall. Now the unblock also ends the block (`LiftIncident`, as the agent API's lift does). "Freigeben" on Sperren opens the unblock of the incident (false positive or not, the address as an own IP if wanted).
- **Firewall state.** Per row `banned` (the firewall applied a revision that holds it), `pending` (not yet, or the gateway restarted and no longer knows the revision applied), `stale` (no call for 2 minutes, or the firewall reports an error), `off` (no call ever). For the list `ok`, `error` with the firewall's error line, `stale`, `off`, with the time of the last call and the clients held.
- **Dashboard.** "Verhalten & Limits" is gone as a page. Its settings, scenarios and limits, are "Szenarien und Limits" below Regeln (`/settings/rules/behaviour`), with a block "Über mehrere Anfragen" on the overview of Regeln: the rules block a request, scenarios and limits the address. What happened is the new page "Sperren" (`/blocks`) below Schutz: "Gesperrte Adressen" (this list), "Gestoppte Anfragen" (the incidents of every website of the last 7 days with the search for an incident number, before the page Vorfälle), "Verlauf" (the hits) and "Wellen". `/behaviour` and `/incidents` lead there; one incident keeps its page `/incidents/<number>`.

## D86 Single rules are taken out of an exception (2026-11-14, initiator)

- **Finding (initiator).** Exceptions could only be set and removed. When one rule of a field left out for 91 rules should check again, the only way was to remove the whole entry and set 90 rules again.
- **No editing form.** Another website, page or field is another reach: removing and setting a new exception shows that, an edit would hide it. Who set an exception and when stays true only when nobody else changes it. Adding rules already works: a new exception for the same field joins the same entry (D84).
- **Taking a rule out.** Client dashboard API `DELETE /rule-exceptions/{id}/rules/{rule}` (`removeRuleExceptionRule`), agent API `removeAgentException` with the optional `rules` in its body (`AgentExceptionRemoveRequest`, 1 to 16 ids, each once). The exception keeps its id, reason, author and time and holds the other rules; taking out every rule it holds removes it. A rule the exception does not hold answers 404, like an unknown id. One write under the same lock as setting and removing, so a failed build leaves nothing half done.
- **Events.** `schild.rule.exception_removed.v1` with the exception's id and only the rules taken out; the event schema is unchanged. Whoever reads the history sees which rules apply again, the list shows what stays.
- **Dashboard.** An × next to every rule number of an entry, with a confirmation that names the rule and how many stay excepted. For the last rule it says that the exception goes.

## D85 Less is redacted: the User-Agent as sent, tokens only when they look random (2026-11-13, initiator)

- **Finding (initiator, live test).** The dashboard showed `[redacted]` where nothing secret was: the User-Agent of an app read `[redacted].1.29.10.33 …`, because a long app name with a build number matched the token pattern (24 characters with a letter and a digit). The same pattern hit long slugs and file names in paths, and parameter names like `zipcode` or `monkey` counted as secret because they end in `code` or `key`.
- **Not removed altogether.** Password reset and magic links carry their token in the path or the query string, and what is stored is read in the dashboard, by agents with a read token and in `privacy/export`. The public promise stays: passwords and tokens are redacted, request bodies are never stored.
- **User-Agent.** Stored as sent, cut to 1024 bytes, control characters removed as before (amends D50). It names software; the contact address of a crawler is public.
- **Tokens in paths, query values and rule messages.** 32 characters or more of the base64/hex alphabet, of which at least half sit in parts that hold both a digit and a letter. A reset token, a hash, a UUID and a base64url value still match; a slug, a file name with a date, an app name do not. JWTs and e-mail addresses are redacted as before.
- **Secret parameter names.** Long names match as before at the start or the end of a name (`token`, `password`, `secret`, `session`, `signature` …). Short ones (`key`, `pass`, `pin`, `sid`, `auth`, `hash`, `sig` …) count only as a word of their own (`api_key`, `apiKey`), no longer as the end of another word. `code` is secret on its own (OAuth) and in `auth_code`, `reset_code`, `access_code`, `invite_code`, `verification_code`, `passcode`, not in `zip_code` or `country_code`.
- **Stored data.** What was written before D85 stays as it was redacted; it ages out with the retention (14 days).
